> 版本：v0.9
> 更新日期：2026 年 7 月 27 日
> 状态：模块解耦、行为保持式迁移与诊断规范冻结稿
> 本文规定代码、模块、场景、资源、测试、Git和AI协作规范；技术选型见《光速奇点_技术栈_v0.9》。
> 实施状态说明：本文同时包含当前规范与目标架构规范。未实现模块必须明确标注，不得把目标接口写成当前能力。

# 1. 总原则

## 1.1 核心原则

1. 核心循环不得包含具体光形态实现。
2. 核心循环只保留初始化、依赖校验、信号连接、生命周期协调、全局状态切换和重置入口。
3. 发射器只生成统一发射请求。
4. 光运行协调器根据光形态选择对应执行模块。
5. 光线和光粒共享协议，不强行共享具体算法。
6. 核心循环只依赖稳定公共接口，不直接引用具体机关和视觉节点。
7. 模块内部状态只能通过公共方法修改。
8. 跨模块结果优先使用信号、不可变结果对象或明确返回值。
9. 光传播模块只依赖只读世界查询接口。
10. 水晶和机关通过统一交互事件接收传播结果。
11. 逻辑传播与视觉显示分离。
12. 新增机关、光形态和目标原则上不修改核心循环。
13. 不创建包办全部职责的巨型 `GameManager`、`VisualManager` 或全局事件总线。
14. 架构冻结的是公共契约，不是内部每一行实现。

## 1.2 行为保持式迁移

现有代码不得推倒重写。

迁移流程：

```text
记录当前行为
→ 为现有逻辑建立公共接口
→ 原函数或等价逻辑迁入对应模块
→ 核心循环改为引用模块
→ 自动检查
→ 人工回归
→ 合并
→ 再抽离下一职责
```

必须复用当前已经验证的：

- `GridMetrics`；
- `OccupancyRegistry`；
- `PlaceableToken`；
- 单格镜面反射；
- `BasicCrystal`；
- `ObjectVisualView` 和视觉 Profile；
- `InventorySlotView`；
- `LightSegmentView`；
- 当前拖拽、移动、回收和回滚；
- 当前运行状态与权限；
- 当前移动次数计算；
- 当前 R 完整重置；
- 当前普通光线传播算法和安全上限；
- 当前启动期自检。

禁止先删除旧实现再整体重写。

当前状态基线（真实运行状态）：

```text
SETUP
PULSE_ACTIVE
MOVE_WINDOW
COMPLETED
```

当前运行状态所有权已迁出核心：

- `RunStateController`（`gameplay/interaction/run_state_controller.gd`，`RefCounted`）已实现并接入 `core_loop_prototype`，是当前运行状态的唯一所有者；
- `core_loop_prototype` 不再持有 `current_run_state`，核心不直接写状态，而是通过 `begin_pulse()`、`finish_pulse()`、`reset_to_setup()` 请求转换；
- `pulse_generation`、`runtime_moves_used`、发射编排、异步过期保护与 R 完整顺序由 `LevelRuntimeController`（`gameplay/runtime/`）唯一持有；
- `is_level_completed` 与完成事实由 `ObjectiveController` 唯一持有；
- 拖拽业务由 `DragFlowController` 拥有，玩家机关映射与放置/移动/回收事务由 `PlacementController` 拥有，库存事实由 `InventoryController` 拥有，普通光路视觉由 `LightVisualController` 拥有，七项自检编排由 `StartupSelfCheckCoordinator` 拥有；
- `core_loop_prototype.gd` 已降至约 480 物理行，只负责场景引用、依赖组装、输入顶层转发、右键入口、节点工厂、UI 适配与启动接线，这不代表 9 月 5 日交付或完整统一光运行架构完成；
- `RuntimeStateRules` 保持纯规则层，`RuntimeMoveRules` 保持独立。

当前不包含：

- `READY_TO_FIRE`；
- 开始运行按钮。

# 2. 模块职责规范

## 2.1 单一职责

每个模块必须明确：

- 负责什么；
- 输入是什么；
- 输出是什么；
- 修改哪些状态；
- 发出哪些信号；
- 不负责什么。

## 2.2 核心循环

允许：

- 保存模块引用；
- 校验依赖；
- 连接信号；
- 接收开始运行、发射、重置等高层请求（目标职责；不代表当前 UI 或状态门已经存在，当前实施仍使用原型四状态）；
- 协调运行状态；
- 接收统一执行结果；
- 请求目标判断；
- 协调完整重置。

禁止：

- 逐格计算光线路径；
- 推进光粒 Tick；
- 直接判断镜面；
- 直接激活水晶；
- 管理库存数量；
- 处理鼠标拖拽事务；
- 创建具体光路纹理；
- 直接读写占用表内部字典；
- 写入日志文件；
- 保存具体关卡对象数组。

## 2.3 模块引用

正确：

```gdscript
inventory_controller.commit_take(item_id)
run_state_controller.enter_execution()
light_runtime.execute(request)
```

错误：

```gdscript
inventory_controller.remaining -= 1
run_state_controller.current_state = RunState.PULSE_ACTIVE
particle_module.active_particles.clear()
```

引用其他模块时只能调用公开契约，不得直接修改内部字段。

## 2.4 依赖方向

推荐：

```text
核心协调层
→ 公共协议和控制器
→ 具体玩法模块
→ 基础网格、资源与数据
```

禁止：

- 基础网格依赖核心循环；
- 视觉组件修改传播逻辑；
- 传播模块直接操作UI；
- 机关脚本直接修改库存；
- 关卡场景脚本修改全局存档内部结构；
- 诊断模块修改被检查模块状态。

# 3. GDScript规范

## 3.1 静态类型

- 公共函数必须写参数类型；
- 公共函数必须写返回类型；
- 重要局部变量写类型；
- 使用稳定类型对象代替结构任意变化的 Dictionary；
- `Dictionary` 只用于清楚、局部、可验证的数据场景；
- 禁止依赖隐式类型造成跨模块不确定性。

## 3.2 中文注释

每个模块顶部必须说明：

- 模块职责；
- 系统位置；
- 主要依赖；
- 明确不负责的内容。

每个新增或修改函数使用中文 `##` 文档注释，说明：

- 职责；
- 输入；
- 输出；
- 副作用；
- 边界和停止条件。

关键逻辑必须有中文行内注释：

- Tick 批次；
- 原子提交和回滚；
- 脉冲版本失效；
- 状态窗口；
- 移动次数扣除；
- 占用更新；
- 方向映射；
- 编辑器吸附；
- 日志轮转；
- R 重置。

禁止无信息价值的逐行复述。

## 3.3 命名

- 类名：`PascalCase`；
- 文件：`snake_case.gd`；
- 私有字段和函数：以下划线开头；
- 稳定状态ID：小写英文 `StringName`；
- 布尔值使用 `is_`、`has_`、`can_`；
- 请求使用 `request_`；
- 提交使用 `commit_`；
- 校验使用 `validate_`；
- 重置使用 `reset_`。

# 4. 场景与节点规范

## 4.1 可复用对象

独立、可复用、拥有身份和运行状态的对象使用 `PackedScene`（`.tscn`）实例化，包括机关、发射器、水晶和视觉组件。同类实例共享同一场景模板与默认不可变资源，但每个实例的节点、位置、方向、身份和运行状态相互独立，不在正式关卡中手工拼接其内部结构。

独立墙块或机关才使用 `PackedScene`；连续地面、普通墙体、可放置区域和装饰优先使用 `TileMapLayer`（见 4.4）。地图级 `Walls` 容器位于地图原点仅是容器组织事实，不代表独立对象的锚点格中心约定错误。

## 4.2 固定节点契约

被脚本依赖的核心子节点名称不得随意修改。修改前必须：

- 搜索全部引用；
- 更新场景和脚本；
- 运行场景；
- 记录接口变更。

## 4.3 编辑器格子对象

`GridPlacedObject`（`gameplay/grid/grid_placed_object.gd`，`@tool`，`extends Node2D`）已实现，是固定格场景对象的公共基础节点。当前状态：

- `Node2D.position` 是唯一持久化的场景放置事实（关卡局部网格坐标系），随场景保存；
- 逻辑 `cell` 是计算属性，由 `position` 经 `GridCoordinateRules.world_to_cell` 确定性派生，不再独立序列化为第二份数据；
- `set_cell` / `cell` setter 通过 `GridCoordinateRules.cell_to_world` 反算并写回 `position`；
- `GridPlacedObject` 根节点自身的局部原点为 `(0,0)`；根节点 `position` 对齐目标格中心（`cell_to_world` 返回格中心世界坐标）；
- 单格对象根 `position` 对齐所属格中心，多格对象根 `position` 对齐明确锚点格中心，占用偏移由已冻结接口 `get_occupied_offsets(p_orientation: int = 0)` / `get_occupied_cells(anchor_cell: Vector2i, p_orientation: int = 0)` 表达，子类可重写；`p_orientation` 为中性方向槽（不是全局方向枚举），`anchor_cell` 由根 `position` 派生、不是第二位置事实；
- 对 64×64 网格，`(32,32)` 只是从格子左上角到格中心的半格偏移，不是根节点局部原点；
- visual、collision、hint 等子节点使用相对根节点的局部坐标，不得统一放到 `(32,32)` 二次补偿，不在子节点重建第二套逻辑位置；
- 不得使用 `Node.name` 作为正式对象 ID。

位置契约经 `GridCoordinateRules`（`gameplay/grid/grid_coordinate_rules.gd`）做纯函数换算，原点隐式为世界坐标 `Vector2.ZERO`，格中心偏移为半格（`CELL_SIZE / 2.0`），不复制 64×64 公式。

编辑器关卡制作方法分两条路径（定义与实施边界见《光速奇点_技术栈_v0.9》）：

- 方法 A：Inspector、视觉 Profile、资源配置——已可用的配置路径；
- 方法 B：2D 视图拖动、64×64 吸附、写回逻辑 `cell`——已完成（D5 落地，Godot 原生 GUI 关卡编辑基础）。

补充：

- 多格对象使用占用偏移，不允许子类建立第二套逻辑位置；
- 当前已有固定对象（如 `EmitterConfigNode`）已继承 `GridPlacedObject`，但不得据此声称全部固定对象已完成迁移。

## 4.4 TileMapLayer

连续地面、普通墙体、可放置区域、禁止区域、地图形状和装饰使用分层 `TileMapLayer`，与独立对象实例化（4.1）采用不同技术路径。图块自定义数据命名稳定，不在多个脚本中复制解释。

# 5. 资源与视觉规范

## 5.1 视觉资源

- 代码不写死图片路径；
- 使用 `.tres` Profile 配置纹理；
- 世界对象和 UI 图标分离；
- 世界单格素材以64×64画布为基础；
- 使用 Nearest 过滤；
- 内容居中；
- 正常纹理默认不使用旧占位颜色染色；
- 合法、非法、禁用反馈使用独立覆盖层或调制接口。

## 5.2 视觉与逻辑分离

视觉不得决定：

- 镜面方向；
- 水晶是否点亮；
- 发射器光形态；
- 机关占用；
- 光传播结果。

逻辑状态通过稳定状态ID驱动视觉。

# 6. 光执行规范

## 6.1 通用请求

发射器生成统一 `EmissionRequest`，至少包含：

- 来源ID；
- 起始格；
- 方向；
- 光形态；
- 执行编号；
- 后续需要时包含颜色。

## 6.2 通用协调

> 实施状态说明：本节为目标架构，当前未实现。

`LightRuntimeCoordinator`：

- 接收请求；
- 选择已注册执行模块；
- 防止重复执行；
- 转发开始、交互、完成和失败；
- 取消当前执行；
- 不计算具体传播。

## 6.3 只读世界查询

> 实施状态说明：本节为目标架构，当前未实现。

传播模块只通过 `LightWorldQuery` 查询：

- 地图边界；
- 阻挡；
- 交互对象；
- 目标；
- 当前光形态是否可通过。

查询接口不得删除墙、移动机关或修改目标。

## 6.4 光线和光粒

共享：

- 发射请求；
- 光形态；
- 交互事件；
- 执行结果；
- 世界查询；
- 开始、完成、失败信号。

独立：

- 算法；
- 时间模型；
- 路径或实体状态；
- 视觉生命周期；
- 稳定判定；
- 终止条件。

# 7. 放置与库存规范

## 7.1 放置事务

正式提交顺序：

```text
接收玩家意图
→ 校验权限
→ 校验目标格
→ 校验占用
→ 预备修改
→ 原子提交
→ 成功后更新库存和UI
→ 失败时完整回滚
```

## 7.2 占用表

`OccupancyRegistry` 只负责：

- 格到机关ID；
- 机关ID到占用格；
- 登记；
- 注销；
- 查询；
- 一致性检查。

不负责：

- 鼠标；
- UI；
- 地图合法区；
- 运行状态；
- 库存；
- 传播；
- 通关。

## 7.3 库存

库存模块负责：

- 总量；
- 剩余；
- 成功放置扣除；
- 回收归还；
- 重置；
- 一致性。

玩家交互模块不得直接修改库存内部字段。

## 7.4 放置查询边界

`PlacementController` 是 `placed_tokens_by_id` 映射与机关序号的唯一所有者。查询边界：

- `get_placed_ids()` 返回当前已放置机关 ID 的快照，返回后映射增删不影响快照；
- `get_placed_node(mechanism_id)` 提供按 ID 的只读节点查询，ID 未登记或节点失效返回 `null`，调用方需自行 `is_instance_valid` 校验；
- 调用方不得直接持有或修改 `PlacementController` 内部映射，光线层等只读消费者经 `get_placed_node` Callable 解析节点；
- 不得恢复已删除的 `get_placed_tokens_by_id_reference()` 等可变 `Dictionary` 暴露接口。

## 7.5 回收事务

回收采用预留两阶段归还，`commit` 成功前不动不可逆事实。正式事务顺序：

```text
确认机关存在
→ 预留库存归还容量
→ 暂时注销占用
→ 提交库存归还
→ 提交成功后才删除稳定 ID 映射并释放 Token
```

失败回滚：

- 预留失败：不注销占用、不删映射、不释放 Token，全部保持；
- 注销占用失败：取消预留，节点/映射/库存保持；
- 提交归还失败：用正式注册接口恢复原占用、取消预留，保留 Token 与身份映射，事务一致可重试；
- 占用恢复失败必须显式 `push_error` 报告不变量破坏，不得静默吞掉。

调用方不得直接修改库存或占用模块的内部 `Dictionary`，归还与注销一律经各模块正式公共接口。

# 8. 诊断、日志与自检

源代码放在：

```text
gameplay/diagnostics/
```

技术测试放在：

```text
tests/
```

运行生成文件放在：

```text
user://diagnostics/
```

当前实现基线：

已实现：

- `DiagnosticsController`；
- `RuntimeLogger`；
- `RuntimeSnapshotData`、序列化、写入结果和文件保存能力；
- `SelfCheckCallable`；
- `SelfCheckResult`；
- `SelfCheckRunResult`；
- `SelfCheckRunner`；
- `StartupSelfCheckCoordinator`：整块负责七项自检编排、三层 Debug 硬断言与启动摘要日志，核心只采集场景数据并调用 `run_all`；
- 七项启动自检统一经过 `DiagnosticsController`，由协调器按固定顺序构建并执行；
- 全部成功后写入一条 `runtime.log` INFO 摘要。

未实现：

- 真实 `RuntimeSnapshot` 玩法采样；
- Debug 游戏内控制台；
- `log`/`check`/`state`/`clearlog` 命令。

边界：

- Diagnostics 不长期持有玩法节点；
- 不修改玩法状态；
- 不决定游戏是否继续；
- 不承担玩法事务硬断言；
- `RuntimeLogger` 不向 Godot 控制台输出。

RuntimeSnapshot 真实玩法采样前置基础已就绪：

- 稳定 `crystal_id`（`BasicCrystal` 显式配置）；
- `LevelObjectRegistry`；
- `ObjectiveController`；
- `LevelRuntimeController`。

仍需后续确认，因此真实采样继续延期：

- 多水晶统一注册；
- 正式快照采样时点；
- 完整 schema。

明确禁止使用 `Node.name` 作为正式 `crystal_id`。

### 当前组件现状

`RuntimeLogger`：

- 内存缓存日志条目，超限从最旧条目裁剪；
- 对外返回深复制副本，外部修改不影响内部缓冲；
- 稳定五列 Tab 分隔文本格式，字段转义保证单行结构；
- 只向 `user://diagnostics/logs` 安全写盘，拒绝 `res://`、绝对路径与 `..` 逃逸；
- 单文件上限 2 MiB，最多 8 个文件，目录总量约 16 MiB 收敛清理；
- 当前保持单文件追加实现，不因物理行数机械拆分为多文件模块。

`RuntimeSnapshot`：

- 序列化前校验 `RuntimeSnapshotData`；
- 将 Godot 专有类型转换为 JSON 兼容 Variant 树（转换严格限定在私有 JSON 边界内）；
- 经 `JSON.stringify` 序列化为稳定文本；
- 安全保存到 `user://diagnostics/snapshots`，文件名由快照时间戳生成，含数量与容量保留策略；
- 不负责真实运行场景的数据采集，不自动采样、不自动保存；
- 不使用 `Node.name` 作为 `crystal_id`。

`DiagnosticsController`：

- 仅负责窄委托、生命周期、调度和开关，长期只持有 `RuntimeLogger` 一个实例；
- 不反向控制玩法业务，不采集玩法数据，不决定事务提交或回滚。

`SelfCheck`：

- 继续一检查一文件；
- 不因目录文件数量机械分组。

## 8.1 模块内部自检

每个模块公开只读检查方法，例如：

```text
validate_consistency()
validate_state()
build_debug_snapshot()
```

模块自己负责判断本模块不变量。

## 8.2 自检协调器

`SelfCheckRunner` 只负责：

- 调用各模块公开检查；
- 收集结果；
- 输出摘要；
- 不读取内部私有字段；
- 不修复状态。

## 8.3 日志

日志必须结构化：

```text
[时间][等级][模块][执行ID] 消息
```

等级：

- DEBUG；
- INFO；
- WARN；
- ERROR。

禁止每帧、每次鼠标移动或无状态变化时刷日志。

## 8.4 日志轮转与删除

默认值：

- 单个日志文件最大 `2 MiB`；
- 最多保留 `8` 个日志文件；
- 日志目录总量上限 `16 MiB`；
- 单个状态快照最大 `1 MiB`；
- 最多保留 `10` 个快照；
- 快照目录总量上限 `10 MiB`。

超过任意限制：

```text
按修改时间从旧到新排序
→ 删除最旧文件
→ 重新计算数量和容量
→ 直到全部满足
```

清理失败必须记录警告，但不得阻塞游戏主流程。

Debug版：

- 完整日志；
- 自检；
- 调试控制台；
- JSON快照。

Release版：

- 默认只保留 ERROR 和必要启动信息；
- 不开放调试控制台；
- 不输出高频调试日志。

## 8.5 调试命令

Debug游戏内控制台可支持：

- `log`：导出日志和状态快照；
- `check`：执行跨模块自检；
- `state`：显示当前状态摘要；
- `clearlog`：清理当前会话缓冲。

不依赖外部 PowerShell 命令窗口。

# 9. 测试规范

## 9.1 三层测试

1. 模块自检；
2. 技术测试场景；
3. 人工操作回归。

MCP启动无错误不能代替鼠标、键盘和视觉测试。

## 9.2 每次抽离后的回归

至少验证：

- 主场景启动；
- 开始运行按钮（功能实现后必须测试；当前阶段不作为已经存在的回归项）；
- Space；
- R；
- 拖拽；
- 合法和非法放置；
- 移动；
- 回收；
- 镜面；
- 水晶；
- 光路；
- 状态权限；
- 库存；
- 占用一致性；
- 无新错误。

当前回归基线：当前四状态、Space、R、拖拽、占用、库存、镜面、水晶和光路继续测试；开始运行按钮当前阶段不作为已存在回归项。

## 9.3 测试目录

```text
tests/
├─ unit/         # 独立单元测试
├─ integration/  # 预留与后续集成测试
└─ scenes/       # 测试专用场景
```

技术测试场景不进入正式选关。

补充约定：

- `tests/unit` 保存独立单元测试，`tests/integration` 预留后续集成测试，`tests/scenes` 保存测试专用场景；
- 每个测试脚本对应的 `.gd.uid` 应与脚本一同保留，不得单独删除；
- 不得删除整个 `tests` 目录；
- 测试脚本不接入正式启动链（不由主场景或 Autoload 调用）；
- 测试成功以 `quit(0)` 退出，失败以 `quit(1)` 退出。

## 9.4 测试拆分

当前测试按职责拆分，不得继续引用已删除的旧超长单体测试文件：

- `EmitterConfig` 按基础契约、信号、识别、同步、旋转拆分；
- `PlacementController` 按 `place`、`move`、`recycle`、`clear_all` 拆分；
- `DragFlow` 按库存拖拽、已放置拖拽、回收取消、权限回调拆分；
- `LevelRuntime` 按 `fire`、`pulse`、`reset`、`moves`、`boundaries` 拆分；
- CoreLoop Emitter Integration 按场景结构、运行接线、水晶契约拆分。

Fixture 只承担桩、构造、接线与清理；Fixture 不得包含断言、生产业务规则或隐藏关键被测事务。

## 9.5 规模红线

源码文件规模（适用全部 `.gd` 源码；不机械拆分，不得删除必要中文注释压行数）：

- 物理行 `<250`：正常职责检查；
- 物理行 `≥250`：强制职责复查；
- 物理行 `≥350`：强制拆分评估；
- 测试物理行 `>500`：强制复查。

目录规模（`.gd.uid` 不计入目录源码数量）：

- 普通职责目录 `≤6` 主要源码文件：推荐；
- `7～8`：关注职责密度；
- `>8`：强制目录/子目录拆分评估。

多个不相关职责必须拆分；不因行数机械拆分单一职责文件。

# 10. Git规范

- 从最新 `main` 创建分支；
- 一个分支只做一个明确任务；
- 一次PR不混入无关重排；
- 同一时间避免多人修改同一个 `.tscn`；
- 公共接口变更先讨论；
- 至少一名队友运行或审查；
- 合并后确认 `main` 可运行；
- 删除已完成分支；
- AI 不执行 Git 写操作。

提交前：

```text
git status
git diff
git diff --check
Godot运行
人工测试
只读审查
```

# 11. AI协作规范

## 11.1 推荐分工

- GPT-5.6 Thinking：整体架构、讨论和提示词；
- GPT-5.5：本地文档、只读审计、复杂诊断；
- GLM-5.2：范围明确的实施、MCP验证和常规修复；
- 用户：人工测试、Git写操作和最终决策。

## 11.2 提示词必须包含

- 目标；
- 明确不做；
- 允许修改文件；
- 禁止修改文件；
- 完成标准；
- 自动测试；
- 人工测试；
- 停止条件；
- 中文注释要求；
- 禁止Git写操作。

## 11.3 禁止

- 一次重写整个工程；
- 未读真实代码直接生成；
- 把计划写成已完成；
- 用旧文档覆盖最新决定；
- 未运行就声称测试通过；
- 为目录整齐创建大量空模块；
- 让AI自行解决需求歧义。
