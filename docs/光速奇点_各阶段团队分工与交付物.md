## 1. 文档用途

本文用于明确：

1. 每个项目阶段的目标和完成标准；
2. 每个阶段三名成员分别需要完成什么；
3. 每名成员在该阶段的主要职责；
4. 每名成员需要提交哪些可以检查、运行或验收的结果；
5. 三人必须共同确认哪些公共规则；
6. 当前进度已经到哪里，阶段二还缺什么；
7. 如何避免把“AI 实际写代码”误解为“所有模块都由陈俊贤独自负责”。

“主责”表示该成员负责把对应内容推进到可用、可测试和可合并状态，不表示所有代码都必须由该成员亲手输入，也不表示其他成员可以只提供想法而不提交可验收结果。

对应功能已经通过 PR 合并到 `main`，当前最小拖拽放置分支已经删除。

## 2.2 当前实现的定位

当前的 `PlaceableToken` 是布置系统原型，不是正式光学机关。它只负责：

- 唯一机关 ID；
- 单格逻辑位置；
- 正式放置和拖拽预览；
- 合法、非法视觉反馈；
- 显示和隐藏。

它当前不负责：

- 反射；
- 阻挡；
- 分光；
- 滤色；
- 水晶判定；
- 运行期移动次数；
- 控制信号。

## 2.3 与 v0.8 正式规则仍存在的差距

当前原型已经验证布置系统，但还不能视为阶段二完成。

正式规则要求：

- 第一次发射后锁定主发射源方向和机关人工配置；
- 运行阶段不能从机关栏拿新机关；
- 运行阶段不能回收机关；
- 运行阶段不能旋转或修改机关配置；
- 只能移动玩家自己放置且标记为可运行期移动的机关；
- 每关受 `runtime_move_limit` 限制；
- 只有成功移动到新合法位置才扣除次数；
- 移动请求需要在安全批次边界原子提交；
- 普通脉冲光线结束后，移动只影响下一次发射；
- 普通独立水晶合法点亮后保持到重置；
- 控制机关的 `MOMENTARY / LATCHED` 生命周期与水晶规则分开。

当前汇报中的原型权限允许在 `PULSE_ACTIVE` 和 `MOVE_WINDOW` 中继续拿取、移动和回收机关，这只是早期原型行为，后续必须按照 v0.8 正式规则收紧。

# 11. 每个任务的统一提交标准

一个任务只有同时满足以下条件才算完成：

```text
功能或内容已经存在
+ 在测试场景或正式关卡中可运行
+ 常见重置和重复进入无明显残留
+ 自动验证与人工验证已区分
+ 至少一名队友检查
+ 通过 PR 合并到 main
+ 已知问题已经记录
```

每个任务至少应提交：

- 功能或内容本体；
- 测试步骤；
- 实际测试结果；
- 已知问题；
- PR 说明；
- 队友检查结果；
- 合并后的 `main` 运行确认。
