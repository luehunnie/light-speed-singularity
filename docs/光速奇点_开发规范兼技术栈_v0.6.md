# 《光速奇点》开发规范兼技术栈

> 版本：v0.6  
> 状态：技术方案更新稿  
> 目标：在控制实现难度的前提下，完整支持已经确定的玩法。

## 1. 技术目标

技术方案应满足：

- 支持固定网格地图；
- 支持一格、两格、三格和四格机关；
- 支持玩家在布置阶段放置、移动、旋转和删除机关；
- 支持发射后锁定机关人工配置；
- 支持运行期间受限移动玩家机关；
- 支持墙体消除器临时关闭可消除墙；
- 支持光粒和光线两套传播规则；
- 支持八方向反射；
- 支持逻辑先后和同时事件；
- 支持顺序水晶和同时水晶；
- 支持持续光线；
- 支持光电二极管、电控门、电动镜面和次级发射器；
- 支持锁存与随动状态；
- 支持机关状态变化后的光路重新计算；
- 保证相同布局得到确定结果；
- 适合三人初次完整开发；
- 便于使用 GitHub 和 AI 编码工具协作；
- 支持科学家主题成就、右下角弹窗、档案解锁和成就持久化。

## 3. 引擎选择

采用 Godot 4.6.1 Standard。

### 优点

- 已是团队当前环境；
- 适合 2D 网格游戏；
- 场景、节点、Signal 和 Inspector 能覆盖项目需求；
- GDScript 学习成本相对较低；
- Windows 导出直接；
- 适合快速制作测试场景。

### 缺点

- 场景文件多人同时修改容易冲突；
- 初学者容易把逻辑、动画和 UI 写在同一个脚本；
- 复杂状态系统仍然需要自行设计；
- AI 生成代码可能引用旧版 Godot API。

### 实现玩法的困难

Godot 本身可以实现全部玩法。真正困难的不是引擎能力，而是：

- 持续光线状态；
- 运行期间机关移动与光路重算；
- 机关配置锁定和阶段状态机；
- 随动机关；
- 动态光路重新计算；
- 同时和顺序事件；
- 反馈循环终止。

## 4. 编程语言规范

采用静态类型 GDScript，不使用 C#，不混用两套语言。

### 4.1 基本要求

- 公共函数必须写参数类型；
- 公共函数必须写返回类型；
- 重要局部变量尽量写类型；
- 公共枚举统一集中定义；
- 核心状态不使用结构随意变化的 Dictionary；
- 处理重要警告；
- 代码提交前必须能正常运行；
- AI 生成代码必须由提交者理解。

示例：

```gdscript
func get_next_cell(
    cell: Vector2i,
    direction: Vector2i
) -> Vector2i:
    return cell + direction
```

### 4.2 不采用 C# 的原因

C# 可以实现全部玩法，但会增加：

- .NET 版本 Godot 环境；
- 新语言学习；
- 构建和导出问题；
- AI 排错范围；
- 团队沟通成本。

对于当前规模，收益不足以抵消额外难度。

## 5. 地图、坐标与机关占用方案

采用：

> `TileMapLayer` 管理静态地图，`Vector2i` 负责格子坐标、方向与传播计算，轻量机关占用表负责多格机关和动态机关查询。

不再预先开发完整的 `GridModel / GridService` 框架。

### 5.1 TileMapLayer 负责

- 地面；
- 墙体；
- 装饰；
- 可放置区域显示；
- 静态地图范围；
- 可消除墙标记与基础墙体查询；
- 世界坐标与格子坐标转换；
- 静态图块的自定义数据。

推荐在 TileSet 自定义数据中保存：

```text
blocks_light
placeable
particle_passable
removable_wall
terrain_type
```

示例：

```gdscript
func world_to_cell(world_position: Vector2) -> Vector2i:
    var local_position: Vector2 = terrain_layer.to_local(world_position)
    return terrain_layer.local_to_map(local_position)

func cell_to_world(cell: Vector2i) -> Vector2:
    return terrain_layer.to_global(
        terrain_layer.map_to_local(cell)
    )
```

### 5.2 Vector2i 负责坐标与方向计算

所有光的逻辑位置使用 `Vector2i`。

八个合法方向统一定义为常量：

```gdscript
const DIR_UP := Vector2i(0, -1)
const DIR_UP_RIGHT := Vector2i(1, -1)
const DIR_RIGHT := Vector2i(1, 0)
const DIR_DOWN_RIGHT := Vector2i(1, 1)
const DIR_DOWN := Vector2i(0, 1)
const DIR_DOWN_LEFT := Vector2i(-1, 1)
const DIR_LEFT := Vector2i(-1, 0)
const DIR_UP_LEFT := Vector2i(-1, -1)
```

下一格直接计算：

```gdscript
var next_cell: Vector2i = current_cell + direction
```

镜面反射也使用向量分量计算或固定映射表。

示例：

```gdscript
func reflect_horizontal(direction: Vector2i) -> Vector2i:
    return Vector2i(direction.x, -direction.y)

func reflect_vertical(direction: Vector2i) -> Vector2i:
    return Vector2i(-direction.x, direction.y)

func reflect_slash(direction: Vector2i) -> Vector2i:
    return Vector2i(-direction.y, -direction.x)

func reflect_backslash(direction: Vector2i) -> Vector2i:
    return Vector2i(direction.y, direction.x)
```

反射前仍然必须判断：

- 是否从合法方向进入；
- 是否与镜面平行；
- 是否撞到长平面镜短边；
- 是否被镜框阻挡。

向量计算只负责得到方向结果，不负责自动判断机关规则。

### 5.3 斜向墙角判断

斜向传播时，检查两个相邻正交格：

```gdscript
func is_diagonal(direction: Vector2i) -> bool:
    return direction.x != 0 and direction.y != 0

func is_diagonal_blocked(
    cell: Vector2i,
    direction: Vector2i
) -> bool:
    if not is_diagonal(direction):
        return false

    var horizontal_cell := cell + Vector2i(direction.x, 0)
    var vertical_cell := cell + Vector2i(0, direction.y)

    return (
        is_cell_blocked(horizontal_cell)
        or is_cell_blocked(vertical_cell)
    )
```

这样可以阻止光从两个墙角之间斜向穿过。

### 5.4 轻量机关占用表

`TileMapLayer` 不单独承担动态机关和多格机关状态。

当前关卡至少保留两个简单记录：

```gdscript
# 格子坐标 → 机关对象或机关 ID
var mechanism_at: Dictionary = {}

# 机关 ID → 该机关占用的全部格子
var occupied_cells_by_id: Dictionary = {}
```

概念示例：

```text
mechanism_at[(4, 3)] = mirror_a
mechanism_at[(5, 3)] = mirror_a

occupied_cells_by_id["mirror_a"] = [
    (4, 3),
    (5, 3)
]
```

这些数据可以由 `PlacementController` 管理，也可以在项目早期直接由 `LevelController` 持有。

首版不要求为它单独建立大型通用框架。

### 5.5 多格机关

两格镜面、三格分光器和四格 T 型分光器必须保存：

- 唯一机关 ID；
- 锚点；
- 朝向或旋转状态；
- 完整占用格列表；
- 机关运行状态。

例如：

```text
mechanism_id: mirror_a
anchor: (4, 3)
orientation: horizontal
occupied_cells:
- (4, 3)
- (5, 3)
```

放置流程：

1. 根据锚点和朝向计算全部占用格；
2. 检查所有格子是否在地图范围内；
3. 检查 TileMapLayer 是否允许放置；
4. 检查占用表中是否已经存在机关；
5. 全部合法后一次性登记全部格子；
6. 创建或显示机关场景。

删除或旋转时，必须先清除旧占用，再登记新占用。

### 5.6 动态机关状态

以下状态不写入 TileMapLayer 作为唯一事实来源：

- 门是否打开；
- 镜面处于哪个方向；
- 二极管是否有信号；
- 锁存是否已经触发；
- 次级发射器是否激活；
- 控制连接目标。

这些状态由机关对象或控制系统保存。

例如：

```text
door_a.is_open = true
mirror_b.state = STATE_B
photodiode_c.has_signal = true
```

TileMapLayer、Sprite 或机关场景只根据状态更新显示。

### 5.7 为什么不能只依赖 TileMapLayer

只使用 TileMapLayer 会遇到：

- 多格图块无法自然表示同一个机关整体；
- 删除或旋转时难以同步清理全部格子；
- 动态门和电动镜面的运行状态难以管理；
- 光电二极管和控制目标关系无法只靠图块表达；
- 运行时图块更新与逻辑处理时机可能不同；
- 测试传播规则时必须加载完整地图和场景。

因此本项目采用的不是“只用 TileMapLayer”，而是：

```text
TileMapLayer：静态地图与视觉基础
Vector2i：坐标、方向和传播计算
机关占用表：多格机关与格子查询
机关对象：动态状态
```

### 5.8 实现难度

该方案比完整的 `GridModel / GridService` 更容易开始。

首阶段只需要完成：

1. TileMapLayer 坐标转换；
2. 静态墙体和可放置区域查询；
3. 单格机关占用；
4. 多格机关占用；
5. 放置、旋转和删除；
6. 根据格子查询机关。

如果后期占用和查询代码明显增多，再将这些字典和函数提取为独立类，不需要在项目开始时提前搭建复杂框架。

### 主要风险

- TileMapLayer 与机关占用表坐标不一致；
- 旋转、删除或运行期移动后旧占用没有清除；
- 动态机关画面和逻辑状态不同步；
- `Vector2i` 方向被写入非法值，如 `(2, 0)`；
- 传播模块绕过统一查询接口直接读取场景节点。

为避免非法方向，应统一使用八个方向常量，并在调试版本中检查：

```gdscript
func is_valid_direction(direction: Vector2i) -> bool:
    return (
        direction != Vector2i.ZERO
        and abs(direction.x) <= 1
        and abs(direction.y) <= 1
    )
```

## 6. 光传播方案

采用：

> 离散格子逻辑模拟 + 视觉事件播放。

不使用物理碰撞和 Tween 作为核心玩法判定。游戏中所谓“碰撞”实际是根据 `Vector2i` 格子坐标、TileMapLayer 数据和机关占用表进行的规则查询。

### 6.1 固定处理顺序

```text
进入格子
→ 检查边界和阻挡
→ 处理机关
→ 处理水晶、检测器或二极管
→ 生成视觉事件
→ 安排下一步传播
```

### 6.2 逻辑与画面分离

逻辑层负责：

- 光进入哪个格子；
- 什么时候进入；
- 是否被阻挡；
- 方向是否改变；
- 是否分光；
- 是否触发目标；
- 是否改变机关状态。

画面层负责：

- 光粒移动动画；
- 光线路径绘制；
- 镜面反射效果；
- 门开关动画；
- 镜面转动；
- 水晶反馈；
- 声音。

画面卡顿不能改变玩法结果。

### 6.3 不采用物理碰撞法的原因

使用 Area2D、碰撞体和 Tween 驱动规则虽然容易原型化，但很难稳定实现：

- 分光；
- 同时水晶；
- 顺序水晶；
- 持续光线；
- 动态门；
- 电动镜面；
- 次级发射器；
- 随动状态；
- 光路重新计算。

### 6.4 物理节点的允许用途

`Area2D`、`CollisionShape2D` 或鼠标命中测试可以用于：

- 判断玩家点击了哪个机关；
- 提供拖拽范围或悬停反馈；
- 处理不影响玩法结果的界面交互。

这些节点不能作为光是否命中墙体、镜面、转换器、水晶或检测器的唯一事实来源。核心传播结果必须来自网格和机关查询接口。

## 7. 逻辑时间

使用整数 Tick 管理传播先后。

### 建议规则

- 光线直向经过一格：增加固定 Tick；
- 光线斜向经过一格：增加更长距离对应 Tick；
- 光粒根据速度档位增加不同 Tick；
- 同一 Tick 的事件必须批量处理；
- 同一 Tick 到达视为同时；
- 控制状态在当前批次结束后统一更新；
- 玩家提交的机关移动也在当前批次结束后统一更新；
- 同一批次中所有光事件必须看到同一份机关占用快照。

### 作用

统一 Tick 用于实现：

- 顺序水晶；
- 同时水晶；
- 分光后的先后；
- 光粒和光线混合；
- 次级发射器；
- 动态机关更新；
- 运行期间移动机关；
- 墙体消除器切换墙体阻挡状态。

### 主要困难

- 同一 Tick 事件不能逐个即时修改全局状态；
- 需要先收集，再批量结算；
- 动态状态变化后需要开启新的计算阶段。

## 8. 光状态结构

采用一个受限制的 `LightState`，避免两个独立状态类增加开发难度。

概念字段：

```text
mode
cell
direction
speed_level
ray_color
source_id
logical_tick
```

规则：

- 光粒模式下 `ray_color` 必须为 `NONE`；
- 光线模式下颜色必须是 `WHITE / RED / GREEN / BLUE`；
- 光粒使用速度字段；
- 光线不使用速度字段；
- 通过工厂函数创建光粒和光线；
- 传播前运行状态合法性检查；
- 禁止外部脚本随意修改内部字段。

示例结构：

```gdscript
class_name LightState
extends RefCounted

var mode: LightMode
var cell: Vector2i
var direction: Vector2i
var speed_level: SpeedLevel
var ray_color: RayColor
var source_id: StringName
var logical_tick: int
```

### 工厂函数

```gdscript
static func create_particle(...) -> LightState:
    # ray_color 必须为 NONE
    pass

static func create_ray(...) -> LightState:
    # 必须有合法光线颜色
    pass
```

### 合法性检查

```gdscript
func is_valid() -> bool:
    if mode == LightMode.PARTICLE:
        return ray_color == RayColor.NONE
    return ray_color != RayColor.NONE
```

## 9. 推荐模块划分

```text
LevelController
├─ RunStateController
├─ TerrainLayer（TileMapLayer）
├─ PlacementController / OccupancyRegistry
├─ PropagationSimulator
├─ ObjectiveController
├─ ControlSignalController
└─ VisualController
```

### 9.1 LevelController

负责：

- 初始化关卡；
- 读取关卡元信息；
- 连接各模块；
- 开始发射；
- 重置运行；
- 重置关卡；
- 接收通关结果；
- 协调 RunStateController、传播、放置和目标模块。

不负责：

- 具体镜面反射；
- 具体水晶规则；
- 具体画面动画。

### 9.2 RunStateController

负责管理关卡的运行状态机：

```text
SETUP（布置）
→ RUNNING（运行）
→ SETTLING（停止发射后结算剩余事件）
→ SETUP 或 COMPLETED
```

具体职责：

- 开始发射并锁定玩家机关配置；
- 判断当前操作是否允许；
- 接收停止发射请求；
- 判断传播队列、移动队列和控制信号是否已经稳定；
- 在运行结束或重置时解除配置锁定；
- 防止界面层直接修改运行状态。

不负责具体光传播、占用计算和机关规则。

### 9.3 TerrainLayer

使用 Godot 官方 `TileMapLayer`，负责：

- 静态地图显示；
- 墙体、可放置区域和可消除墙；
- TileSet 自定义数据；
- 根据临时失效表返回墙体当前是否阻挡；
- 世界坐标与格子坐标转换。

### 9.4 PlacementController / OccupancyRegistry

负责：

- 布置阶段的机关放置、移动、旋转和删除；
- 运行阶段的受限移动请求与移动队列；
- 机关配置锁定状态检查；
- 单格与多格机关占用；
- `mechanism_at` 查询；
- `occupied_cells_by_id` 维护；
- 放置合法性；
- 固定机关和玩家机关登记；
- 墙体消除器与被临时关闭墙体的对应关系。

该模块保持轻量，不承担光传播、水晶和控制信号逻辑。

### 9.5 PropagationSimulator

负责：

- 光粒传播；
- 光线传播；
- Tick 队列；
- 八方向反射；
- 斜向墙角判断；
- 分光；
- 滤光；
- 形式转换；
- 循环终止；
- 产生传播事件；
- 机关移动或墙体阻挡变化后的光线全量重算；
- 保证光粒不会因后续移动回溯已经完成的路径。

### 9.6 ObjectiveController

负责：

- 基础水晶；
- 颜色水晶；
- 光形式水晶；
- 同时水晶；
- 顺序水晶；
- 全部目标完成判断。

### 9.7 ControlSignalController

负责：

- 光电二极管；
- 控制连接；
- 锁存；
- 随动；
- 电控门；
- 电动镜面；
- 次级发射器；
- 状态批量更新；
- 重复状态检测。

### 9.8 VisualController

负责：

- 光粒动画；
- 光线路径；
- 门开关；
- 镜面旋转；
- 水晶反馈；
- 声音；
- 调试显示。

不直接决定玩法结果。

## 10. 全局单例规范

只把真正跨场景的服务设为 Autoload。

建议：

- `GameFlow`；
- `SaveManager`；
- `AchievementManager`；
- `AudioManager`，有需要时再加入。

不要设为 Autoload：

- `RunStateController`；
- `PlacementController`；
- `OccupancyRegistry`；
- `PropagationSimulator`；
- `ObjectiveController`；
- `ControlSignalController`。

禁止建立包含全部逻辑的巨大 `GameManager`。

## 11. 机关配置方式

机关和水晶采用：

> 独立场景 + Inspector 导出属性。

示例属性：

```gdscript
@export var mechanism_id: StringName
@export var input_direction: Vector2i
@export var rotation_state: int
@export var activation_mode: ActivationMode
@export var target_ids: Array[StringName]
@export var player_owned: bool = false
@export var movable_during_run: bool = false
@export var configuration_locked: bool = false
```

水晶示例：

```gdscript
@export var crystal_type: CrystalType
@export var group_id: StringName
@export var sequence_index: int
```

### 优点

- 关卡成员可以直接配置；
- 不需要先开发关卡编辑器；
- 比复杂 Resource 嵌套容易理解；
- 适合当前项目规模。

### 缺点

- 配置分散在场景节点；
- 场景文件改动较多；
- 多人同时改同一场景容易冲突。

## 12. 关卡数据

使用简单的 `LevelData.tres` 保存：

- 关卡 ID；
- 关卡名称；
- 初始光形式；
- 可用机关；
- 机关数量；
- 下一关 ID；
- 教学提示；
- 章节信息。

不为每个机关建立复杂 Resource 层级。

## 13. 机关连接

光电二极管和被控机关使用唯一 ID 连接。

关卡加载时建立：

```text
机关 ID → 机关对象
```

规则：

- 一个二极管可控制多个机关；
- 一个受控机关首版只接受一个信号来源；
- ID 必须唯一；
- 目标 ID 必须存在。

启动关卡时应检查：

- 重复 ID；
- 缺失目标 ID；
- 多格机关重叠；
- 机关越界；
- 顺序水晶编号不连续；
- 分光器端口被阻挡；
- 可消除墙缺少对应标记；
- 墙体消除器初始位置非法；
- 玩家机关的运行期移动权限配置错误；
- 关卡初始状态非法。

## 14. 模块通信

采用：

- 需要立即得到返回结果：普通函数调用；
- 某件事已经发生：Godot Signal；
- 跨场景长期状态：少量 Autoload。

避免：

- 大量 `get_parent().get_node()`；
- 任意模块直接修改其他模块内部变量；
- 全局万能 EventBus；
- 机关直接负责通关、存档和切场景。

## 15. 动态控制与重新计算

控制状态在当前 Tick 批次结束后统一应用。

流程：

```text
处理同一 Tick 的传播事件
→ 收集二极管信号和玩家移动请求
→ 结束当前批次
→ 校验并提交玩家机关移动
→ 更新门、镜面、次级发射器和临时墙体状态
→ 判断状态是否变化
→ 重新计算受影响光路
→ 进入下一阶段
```

### 重复状态检测

为防止随动机关无限振荡，记录全局受控机关状态。

例如：

```text
door_a=open
mirror_b=state_1
emitter_c=active
```

如果同一状态组合再次出现，停止本次运行。

### 主要困难

这是整个项目风险最高的技术部分：

- 门变化后旧光线需要清除；
- 镜面变化后路径需要重新生成；
- 随动信号可能反复出现和消失；
- 次级发射器可能引发新一轮传播；
- 机关可能形成反馈循环。

### 简化要求

- 一个受控机关只有一个信号来源；
- 正式关卡避免无法稳定的振荡结构；
- 次级光粒发射器采用上升沿单次发射；
- 状态在批次结束后统一改变；
- 检测到重复状态后停止运行。

## 16. 运行阶段编辑与墙体消除器

### 16.1 操作权限

运行阶段使用白名单控制操作：

允许：

- 选择玩家自己放置的可移动机关；
- 提交移动到合法目标格的请求；
- 移动墙体消除器；
- 停止发射；
- 重置本次运行。

禁止：

- 新增或回收机关；
- 删除机关；
- 旋转机关；
- 修改输入端、输出方向、滤光颜色、检测条件或转换模式；
- 移动关卡预置机关、水晶、检测器和受控机关。

操作权限必须由 `RunStateController` 和 `PlacementController` 共同检查，不能只依赖按钮是否隐藏。

### 16.2 移动请求队列

移动操作不能在鼠标拖拽过程中直接改写核心占用表。推荐流程：

```text
玩家选择目标格
→ 预检查范围、占用和权限
→ 创建 MoveRequest
→ 当前 Tick 批次处理完成
→ 再次校验目标格
→ 原子性清除旧占用并登记新占用
→ 发出 mechanism_moved 事件
```

概念结构：

```text
mechanism_id
from_anchor
to_anchor
requested_tick
request_order
```

同一 Tick 存在多个移动请求时，按照确定的请求顺序处理；后处理请求若与已经提交的新占用冲突，则拒绝该请求并给出视觉反馈。

### 16.3 光粒处理

- 光粒事件使用移动提交后的新占用继续传播；
- 已经完成的 Tick 不回滚；
- 已经经过某格的光粒不会因为机关后来移动到该格而重新处理；
- 移动提交前已经排入同一 Tick 的其他事件继续使用该批次开始时的占用快照。

### 16.4 光线处理

首版采用确定性优先的全量重算：

1. 机关移动或墙体阻挡状态改变；
2. 清除当前逻辑光线路径；
3. 保留发射源、受控机关和目标的当前状态；
4. 从全部活动光线发射源重新计算；
5. 重新生成视觉路径。

暂不实现复杂的局部依赖图和增量重算。

### 16.5 墙体消除器

墙体消除器不直接删除 TileMap 图块。技术上采用“临时失效表”：

```gdscript
# 墙体格坐标 → 当前覆盖它的墙体消除器 ID
var disabled_wall_by_cell: Dictionary[Vector2i, StringName] = {}
```

墙体查询应通过统一接口：

```gdscript
func is_wall_blocking(cell: Vector2i) -> bool:
    if disabled_wall_by_cell.has(cell):
        return false
    return terrain_layer_has_blocking_wall(cell)
```

移动墙体消除器时必须原子性完成：

1. 检查新位置是否为 `removable_wall = true`；
2. 移除原墙体格的临时失效记录；
3. 更新道具占用；
4. 写入新墙体格的临时失效记录；
5. 通知传播模块重新计算光线。

重置整个关卡时清空临时失效表。重置本次运行时保留玩家当前布局与墙体消除器当前位置，但停止传播并解除配置锁定。

### 16.6 运行结束判定

`RunStateController` 只有在以下条件全部满足时才能结束运行：

- 活动光粒数量为零；
- Tick 事件队列为空；
- 移动请求队列为空；
- 待处理控制信号为空；
- 没有待启动次级发射器；
- 随动状态稳定；
- 没有待执行的光线重算。

持续光线关卡由玩家先停止发射，再进入 `SETTLING` 状态处理剩余事件。

### 16.7 主要风险与简化

风险：

- 移动请求与同 Tick 光事件看到不同布局；
- 多格机关移动后残留旧占用；
- 光线重算重复触发；
- 墙体视觉恢复但逻辑仍然可穿过；
- 一个墙体消除器被错误用于永久删除多面墙。

简化要求：

- 首版先支持单格机关运行期移动；
- 单格逻辑稳定后再支持多格机关；
- 光线使用全量重算；
- 一个墙体消除器同时只对应一格墙；
- 正式关卡限制可移动机关数量；
- 移动冷却、动画和手感只影响表现，不改变逻辑提交顺序。

## 17. 成就系统

成就系统用于在游戏过程中宣讲戴琼海院士等中国科学家及其科研精神。

### 17.1 AchievementManager

`AchievementManager` 作为跨场景 Autoload，负责：

- 接收玩法模块发出的成就事件；
- 判断成就是否已经解锁；
- 保存解锁状态；
- 将新成就加入弹窗队列；
- 通知成就展示页面刷新对应内容；
- 可选地通知科学家档案页面解锁对应内容。

玩法模块只报告事件，例如完成某关、首次使用某机关或完成某种组合目标。玩法模块不能直接创建弹窗，也不能直接写成就存档。

### 17.2 成就数据

建议使用简单的 `AchievementData.tres` 或统一成就数据表，包含：

```text
achievement_id
title
scientist_name
spirit_keyword
short_description
full_description
icon
archive_entry_id
hidden_before_unlock
```

成就数据和科学家档案内容分开保存。弹窗只读取短文本，成就展示页面读取完整成就说明，科学家档案可继续承载更完整人物资料。

### 17.3 AchievementToast UI

右下角成就弹窗独立为 UI 场景，负责：

- 从右下角进入和退出；
- 显示图标、标题、科学家姓名和简短说明；
- 多个成就排队；
- 不暂停游戏；
- 不拦截无关输入；
- 在不同分辨率下保持在安全区域内。

禁止由每个关卡自行制作成就弹窗。

### 17.4 AchievementGallery

主界面新增“成就展示”按钮，进入统一的 `AchievementGallery` 页面。

页面负责：

- 成就列表或网格展示；
- 已解锁与未解锁状态；
- 成就详情；
- 对应科学家和科研精神说明；
- 成就获得条件；
- 可选的分类、完成度和解锁时间；
- 返回主界面。

未解锁成就应支持隐藏描述，避免泄露关卡解法。

`AchievementGallery` 只读取 `AchievementManager` 提供的数据，不直接修改成就存档。

### 17.5 触发规范

成就由明确的玩法事件触发，优先使用 Signal 或由 `LevelController` 上报。

成就判断不得依赖动画是否播放完成，也不得通过查找 UI 节点判断。

### 17.6 存档

`ConfigFile` 需要保存：

- 已解锁成就 ID；
- 已解锁科学家档案 ID；
- 可选的首次解锁时间。

已经解锁的成就再次满足条件时不重复弹出，除非以后单独设计可重复挑战。

### 17.7 内容规范

- 科学家姓名、成果和精神说明必须来自已审核内容；
- 不在代码中散落人物介绍文字；
- 不使用未经确认的科学家名言；
- 成就文本修改应集中在成就数据文件；
- 成就系统不影响主线解锁和光传播判定。

## 18. 存档方案

## 27. 最终技术选择

当前建议确定为：

- Godot 4.6.1 Standard；
- 静态类型 GDScript；
- TileMapLayer 负责静态地图、坐标转换和图块自定义数据；
- Vector2i 负责格子坐标、八方向和反射计算；
- 使用轻量 `mechanism_at` 与 `occupied_cells_by_id` 记录机关占用；
- 动态机关状态保存在机关对象和控制系统中；
- 暂不开发完整的 `GridModel / GridService`，代码增长后再按需提取；
- 离散整数 Tick 传播；
- 使用 RunStateController 管理布置、运行和结算状态；
- 发射后锁定玩家机关人工配置；
- 运行期间只允许移动玩家自有的可移动机关；
- 移动请求在 Tick 批次结束后原子提交；
- 光粒不回溯，持续光线在布局变化后全量重算；
- 墙体消除器使用临时失效表，不永久删除 TileMap 图块；
- 逻辑与视觉分离；
- 一个受限制的 LightState；
- 机关场景加 Inspector 导出属性；
- 简单 LevelData Resource；
- 普通函数调用加 Signal；
- 少量 Autoload，包括 AchievementManager；
- 状态变化批量应用；
- 重复状态检测；
- 次级光粒发射器使用上升沿单次发射；
- 测试场景和 assert 优先；
- GUT、Docker、CI 和自动导出后置；
- GitHub Desktop、短期任务分支和 Pull Request；
- AI 一次只处理小范围任务；
- 成就弹窗采用统一 AchievementToast UI；
- 主界面提供 AchievementGallery 成就展示入口；
- 成就和科学家档案通过 AchievementManager 解锁并保存。
