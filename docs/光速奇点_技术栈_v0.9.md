# 2. Godot 4.6.1 Standard

## 用途

- 2D场景；
- TileMapLayer；
- Inspector配置；
- Resource数据；
- Signal；
- Timer；
- 输入；
- Windows导出；
- 编辑器工具脚本。

## 采用原因

- 团队当前环境统一；
- 适合小型2D网格游戏；
- 节点和场景利于拆分机关；
- Inspector适合张梓涵配置关卡；
- GDScript迭代速度快；
- MCP可辅助读取、运行和验证。

## 限制

- `.tscn` 多人同时修改容易冲突；
- `@tool` 脚本必须防止编辑器副作用；
- AI可能生成旧版本API；
- 不当使用节点查找会形成强耦合；
- 逻辑确定性需要项目自行设计。

# 3. 静态类型 GDScript

## 用途

- 核心控制器；
- 传播模块；
- 机关；
- 关卡对象；
- UI；
- 诊断；
- 存档。

## 采用原因

- 与Godot集成直接；
- 团队学习成本较低；
- 静态类型能减少AI生成代码的隐式错误；
- 场景脚本和Resource脚本统一；
- 无需引入.NET导出环境。

本项目不采用C#混合开发。

# 4. 网格与地图

## 4.1 `Vector2i`

负责：

- 光的位置；
- 方向；
- 下一格；
- 镜面映射；
- 固定对象Cell；
- 占用格；
- 多格偏移；
- 地图边界。

## 4.2 `GridMetrics`

唯一保存：

- `CELL_SIZE = 64`；
- `HALF_CELL_SIZE = 32`；
- 单格世界尺寸。

不保存地图内容和关卡状态。

## 4.3 `TileMapLayer`

负责：

- 地面；
- 墙体；
- 合法区域；
- 禁止区域；
- 地图形状；
- 装饰；
- Tile自定义数据。

推荐层：

```text
TerrainLayer
WallLayer
LegalAreaLayer
DecorationLayer
```

## 4.4 `GridPlacedObject`

> 目标基类，当前未实现。现有固定对象尚未继承或组合 `GridPlacedObject`，不得声称已经接入。

目标职责：

- Cell 是唯一逻辑事实；
- 占用偏移；
- 编辑器校验。

方法 A（Inspector 修改 cell 后同步世界位置）：正式采用方向，`@tool` setter 当前未实现。

方法 B（2D 编辑器拖动后吸附并回写 cell）：当前未实现，明确延后。

当前阶段不开始 `GridPlacedObject` 的实现。

# 5. 公共架构技术

> 本章节为长期目标架构，当前均未实现。这些内容不是“机关公共接口与最小模板”当前批次要顺手实施的全部范围。

## 5.1 统一发射请求 `EmissionRequest`

> 目标公共协议，当前未实现。

用途：

- 将发射器当前配置封装成稳定数据；
- 隔离发射器和具体传播实现；
- 为光线、光粒和未来形态提供同一入口。

最小字段：

- 来源ID；
- 起始Cell；
- 方向；
- 光形态；
- 执行ID；
- 后续需要时加入颜色。

## 5.2 光形态 `LightForm`

> 目标公共协议，当前未实现。

用途：

- 标记当前请求是光线还是光粒；
- 只描述类型，不执行传播。

当前：

```text
RAY
PARTICLE
```

## 5.3 光运行协调器 `LightRuntimeCoordinator`

> 目标架构，当前未实现。

用途：

- 接收发射请求；
- 根据光形态选择已注册执行模块；
- 统一发出开始、交互、完成和失败；
- 处理取消；
- 隔离核心循环和具体模块。

## 5.4 世界查询 `LightWorldQuery`

> 目标架构，当前未实现。

用途：

- 给传播模块提供只读关卡查询；
- 隔离传播算法和TileMapLayer、注册表、占用表、目标节点。

提供：

- 是否在地图内；
- 是否阻挡；
- 当前格有哪些交互对象；
- 当前格有哪些目标；
- 某光形态是否可通过。

## 5.5 统一交互事件

> 目标架构，当前未实现。

传播模块输出事件，不直接修改具体水晶或机关。事件可包含：

- 执行ID；
- Cell；
- 进入方向；
- 光形态；
- 颜色；
- 到达Tick；
- 来源ID。

# 6. 光线技术

## 模型

- 同步或队列式完整路径计算；
- 八方向；
- 最大传播步数；
- 分支队列；
- 重复状态保护；
- 逻辑结果与视觉分离；
- 路径显示约1秒。

## 当前复用基础

现有普通光线算法、墙体阻挡、镜面查询、水晶命中、最大步数和路径视觉应迁移到 `gameplay/light/ray/`，不重新从零实现。

## 后续扩展

- 分光；
- RGB单色；
- 滤光片；
- 特殊持续光线；
- 多束同Tick目标事件。

# 10. 诊断技术

> Diagnostics foundation 已实现并合并 main。

已实现：

- `DiagnosticsController`；
- `RuntimeLogger`；
- `RuntimeSnapshotData`、序列化结果、写入结果和文件保存能力；
- `SelfCheckCallable`；
- `SelfCheckResult`；
- `SelfCheckRunResult`；
- `SelfCheckRunner`；
- 七项启动自检；
- 日志轮转、数量和容量限制基础；
- 七项全部成功后写入一条 `runtime.log` INFO 摘要（位于 `user://diagnostics/logs/runtime.log`）；
- `InventoryConsistency` 纯数据规则与运行期硬断言边界。

当前实现说明：

- 核心启动链（仅 Debug 构建）采集网格采样格与库存一致性只读快照，调用 `StartupSelfCheckCoordinator.run_all(...)`；
- 协调器按固定顺序构建并执行七项 `SelfCheckCallable`，每项经 `DiagnosticsController.run_self_check()`（每次内部新建 `SelfCheckRunner`）；
- 七项自检总数恒为七，顺序不变，无第八项；
- `RuntimeLogger` 不向 Godot 控制台输出。

`RuntimeSnapshot` 当前能力仅为：调用方提供 `RuntimeSnapshotData` → `DiagnosticsController` → 序列化或保存。真实玩法采样尚未实现。

前置基础已就绪：

- 稳定 `crystal_id`（`BasicCrystal` 显式配置）；
- `LevelObjectRegistry`；
- `ObjectiveController`；
- `LevelRuntimeController`。

仍需后续确认，因此真实采样继续延期：

- 多水晶统一注册；
- 正式快照采样时点；
- 完整 schema。

禁止使用 `Node.name` 作为正式 `crystal_id`。

未实现：

- 真实 `RuntimeSnapshot` 玩法采样；
- Debug 游戏内控制台；
- `log` / `check` / `state` / `clearlog` 命令。

# 12. GitHub与AI工具

## Git

- Git分支；
- Pull Request；
- Issue；
- 小提交；
- 一任务一分支；
- 至少一名队友审查。

## Godot MCP

用于：

- 读取项目；
- 启动场景；
- 获取输出；
- 验证解析和资源错误。

不能代替真实鼠标、键盘和视觉测试。

## AI分工

当前稳定策略：

| 工具 | 主要用途 |
|---|---|
| GPT-5.6sol | 架构讨论、复杂判断、只读审查和最终复核 |
| GLM-5.2 | 范围明确的实施、常规修复和 MCP 验证 |
| CCswitch | 在本地 Claude Code 中切换核心模型 |
| 用户 | 人工测试、Git 写操作和最终决策 |

GPT-5.5 仅作为历史或备用模型，不再作为当前默认审查模型。

Skill 按需使用：

- `superpowers`：任务拆解、实施流程和验证门禁；
- `gstack`：在需要完整代码审查或开发工作流时调用；
- `frontend-design`：前端视觉实现任务；
- `ui-ux-pro-max`：UI/UX 设计与审查；
- `skill-creator`：创建或维护 Skill；
- `find-skills`：确有能力缺口时查找 Skill。

Skill 使用规则：

- Skill 只能按当前任务需要调用；
- 提示词应注明具体 Skill、调用时机和用途；
- 不得默认一次加载全部 Skill。
