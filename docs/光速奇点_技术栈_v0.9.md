# 2. Godot 4.6.1 Standard

## 用途

- 2D场景；
- TileMapLayer；
- Inspector配置；
- Resource数据；
- Signal；
- Timer；
- 输入；
- Windows导出；
- 编辑器工具脚本。

## 采用原因

- 团队当前环境统一；
- 适合小型2D网格游戏；
- 节点和场景利于拆分机关；
- Inspector适合张梓涵配置关卡；
- GDScript迭代速度快；
- MCP可辅助读取、运行和验证。

## 限制

- `.tscn` 多人同时修改容易冲突；
- `@tool` 脚本必须防止编辑器副作用；
- AI可能生成旧版本API；
- 不当使用节点查找会形成强耦合；
- 逻辑确定性需要项目自行设计。

## 4.4 `GridPlacedObject`

> 已实现基类（`gameplay/grid/grid_placed_object.gd`，`@tool`，`extends Node2D`）。已有固定对象（如 `EmitterConfigNode`）已继承该基类，但全部固定对象完成迁移仍进行中，不得声称已经全部接入。

当前职责：

- 位置契约（已实现）；
- 占用偏移接口已冻结（`get_occupied_offsets(p_orientation: int = 0)` / `get_occupied_cells(anchor_cell: Vector2i, p_orientation: int = 0)`，单格默认 `[Vector2i.ZERO]`，多格由子类重写；`p_orientation` 为中性方向槽，不是全局方向枚举；`anchor_cell` 由根 `position` 派生、不是第二位置事实；具体多格子类尚未实现）；
- 经 `GridCoordinateRules` 做 `cell↔position` 纯函数换算，不复制 64×64 公式。

位置契约（已实现）：

- `position` 是唯一持久化的场景编辑事实；
- `cell` 由 `position` 派生（`world_to_cell`），不独立序列化；
- `set_cell` 通过 `cell_to_world` 反算并写回 `position`；
- `GridPlacedObject` 根节点自身的局部原点为 `(0,0)`，根节点 `position` 对齐目标格中心；
- 单格对象根 `position` 对齐所属格中心，多格对象根 `position` 对齐明确锚点格中心；
- 对 64×64 网格，`(32,32)` 只是从格子左上角到格中心的半格偏移（由 `cell_to_world` 内部使用），不是根节点局部原点；
- visual、collision、hint 等子节点使用相对根节点的局部坐标，不得统一放到 `(32,32)` 二次补偿。

编辑器关卡制作方法（定义与实施边界）：

- 方法 A：Inspector、视觉 Profile、资源配置——当前可用的配置路径；
- 方法 B：2D 视图拖动、64×64 吸附、写回逻辑 `cell`——单格路径已完成（D5，Godot 原生 GUI 关卡编辑基础）；多格对象编辑流程仍为目标，未完成部分必须写为未完成；
- 不得把旧 D2 / D2.5 临时探针或临时插件写成当前方案。

`GridPlacedObject`、`EmitterConfigNode`、`EmissionPreview` 均为 `@tool` 脚本，须防止编辑器副作用。

# 5. 公共架构技术

> 本章节记录公共架构技术。其中世界查询与发射请求的当前真实结构已实现（见 5.1、5.4）；光运行协调器与统一交互事件仍为目标架构，当前未实现。这些内容不是"机关公共接口与最小模板"当前批次要顺手实施的全部范围。

## 5.1 统一发射请求 `EmissionRequest`

> 目标公共协议，当前未完整实现。

用途：

- 将发射器当前配置封装成稳定数据；
- 隔离发射器和具体传播实现；
- 为光线、光粒和未来形态提供同一入口。

最小字段：

- 来源ID；
- 起始Cell；
- 方向；
- 光形态；
- 执行ID；
- 后续需要时加入颜色。

当前真实结构：`FireRequest`（`gameplay/light/fire_request.gd`，`RefCounted`）已实现，承载一次普通光线主发射所需的纯数据——起始格、方向、传播最大步数，由 `FixedEmitter.build_fire_request()` 构造，核心 `fire_light()` 据此调用执行模块。`FireRequest` 是 `EmissionRequest` 目标协议的当前子集，尚未包含来源ID、光形态、执行ID、颜色等统一字段。

## 5.2 光形态 `LightForm`

> 目标公共协议，当前未实现。

用途：

- 标记当前请求是光线还是光粒；
- 只描述类型，不执行传播。

当前：

```text
RAY
PARTICLE
```

## 5.3 光运行协调器 `LightRuntimeCoordinator`

> 目标架构，当前未实现。

用途：

- 接收发射请求；
- 根据光形态选择已注册执行模块；
- 统一发出开始、交互、完成和失败；
- 处理取消；
- 隔离核心循环和具体模块。

## 5.4 世界查询 `LightWorldQuery`

> 已实现。`LightWorldQuery`（`gameplay/world/light_world_query.gd`，`RefCounted`）与 `LevelWorldQuery`（`gameplay/world/level_world_query.gd`，`RefCounted`）均已存在。

用途：

- 给传播模块提供只读关卡查询；
- 隔离传播算法和 TileMapLayer、注册表、占用表、目标节点。

当前提供：

- 是否在地图内（`is_in_bounds`）；
- 是否阻挡（`is_wall_cell`）；
- 当前格的交互对象（`get_light_mechanism_at` / `has_crystal_at`）。

`LevelWorldQuery` 在 `LightWorldQuery` 基础上额外提供放置格合法性校验（`is_valid_placement_cell`）与按 ID 的只读机关节点查询（`get_mechanism_node`，经 `PlacementController.get_placed_node` Callable）。查询接口不得删除墙、移动机关或修改目标。

## 5.5 统一交互事件

> 目标架构，当前未实现。

传播模块输出事件，不直接修改具体水晶或机关。事件可包含：

- 执行ID；
- Cell；
- 进入方向；
- 光形态；
- 颜色；
- 到达Tick；
- 来源ID。

# 6. 光线技术

## 模型

- 同步或队列式完整路径计算；
- 八方向；
- 最大传播步数；
- 分支队列；
- 重复状态保护；
- 逻辑结果与视觉分离；
- 路径显示约1秒。

## 边界

- 光线传播基于逻辑格步进与只读世界查询（`LightWorldQuery`），不依赖 Godot 物理碰撞模拟（`PhysicsBody2D` / `Area2D` / `RayCast`）；
- Godot 画面节点只负责显示与编辑，不作为唯一规则事实；
- 逻辑网格统一使用 `Vector2i`，世界节点 `position` 由格坐标派生或写回。

## 当前复用基础

现有普通光线算法、墙体阻挡、镜面查询、水晶命中、最大步数和路径视觉应迁移到 `gameplay/light/ray/`，不重新从零实现。

## 后续扩展

- 分光；
- RGB单色；
- 滤光片；
- 特殊持续光线；
- 多束同Tick目标事件。

- `RuntimeLogger` 不向 Godot 控制台输出。

`RuntimeSnapshot` 当前能力仅为：调用方提供 `RuntimeSnapshotData` → `DiagnosticsController` → 序列化或保存。真实玩法采样尚未实现。

# 12. 美术资源编辑插件

当前只有一个正式 Godot EditorPlugin：`addons/light_speed_art_profile/`，已在 `project.godot` 的 `[editor_plugins]` 中启用。插件入口为 `plugin.gd`（`@tool`，`extends EditorPlugin`），创建右侧 Dock 并监听编辑器选择。插件内部分为 `target`（目标解析）、`browser`（资产浏览）、`dock`（Dock 与面板）、`editing`（编辑服务）等目录，但这些都属于同一插件内部组织，不得写成多个插件。

已实现能力：

- Profile 目标解析（`VisualTargetResolver`）：将编辑器选择解析为可视目标；
- 美术资产目录浏览（`ArtAssetBrowserModel` / `ArtAssetCatalog`）；
- 状态选择：在当前 Profile 的视觉状态间选择；
- 当前状态图片替换（`VisualStateEditService.replace_with_undo_redo`）；
- Undo / Redo：经编辑器 `EditorUndoRedoManager`（真实编辑器）与 `UndoRedo`（headless 测试）按 `get_class()` 分发；
- Profile 保存确认（`ProfileSaveService`）；
- 共享 Profile 影响警告（`ProfileActionPanel.refresh_shared_hint_for`）。

尚未实现：

- 一键创建独立 Profile 副本；
- 将共享 Profile 自动转换为实例独立资源；
- 未经代码核实的其他高级编辑能力。

边界：

- 插件只读写视觉 Profile 与纹理资源配置，不修改玩法逻辑、光传播或运行状态；
- `@tool` 脚本须防止编辑器副作用，非 `@tool` Resource 在编辑器中调用须以 `Engine.is_editor_hint()` 与 `Script.can_instantiate()` 守卫。
