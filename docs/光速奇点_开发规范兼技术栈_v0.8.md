# 《光速奇点》开发规范兼技术栈

> 版本：v0.8  
> 状态：水晶复合条件、组窗口与点亮视觉技术修订稿  
> 目标：在控制实现难度的前提下，完整支持已经确定的玩法。

## 1. 技术目标

技术方案应满足：

- 支持固定网格地图；
- 支持一格、两格、三格和四格机关；
- 支持玩家在布置阶段放置、移动、旋转和删除机关；
- 支持第一次发射后锁定机关人工配置；
- 支持每关可配置的运行期移动次数；
- 支持运行期间受限移动玩家机关，并在安全批次边界原子提交；
- 支持墙体消除器临时关闭可消除墙；
- 支持光粒和光线两套传播规则；
- 支持普通主发射源的脉冲光线；
- 支持光线约 1 秒显示窗口与脉冲结束清理；
- 支持光粒不留下持续轨迹；
- 支持光电二极管和受控机关的瞬时/随动与锁存生命周期；
- 支持水晶光形式、颜色和组规则的可组合条件；
- 支持普通独立水晶保持到重置，以及同时组和顺序组的固定完成窗口；
- 支持水晶未点亮半透明、点亮完全不透明的统一视觉状态；
- 支持八方向反射；
- 支持逻辑先后和同时事件；
- 支持顺序水晶和同时水晶；
- 仅在明确的特殊机关或关卡中支持持续光线；
- 支持光电二极管、电控门、电动镜面和次级发射器；
- 支持状态到期、批量恢复与锁存保留；
- 支持特殊持续光线在机关状态变化后的全量重新计算；
- 保证相同布局、发射次数、移动次数和操作时序得到确定结果；
- 防止玩家通过无限移动机关绕过关卡设计；
- 适合三人初次完整开发；
- 便于使用 GitHub 和 AI 编码工具协作；
- 支持科学家主题成就、右下角弹窗、档案解锁和成就持久化。

## 3. 引擎选择

采用 Godot 4.6.1 Standard。

### 优点

- 已是团队当前环境；
- 适合 2D 网格游戏；
- 场景、节点、Signal、Timer 和 Inspector 能覆盖项目需求；
- GDScript 学习成本相对较低；
- Windows 导出直接；
- 适合快速制作测试场景。

### 缺点

- 场景文件多人同时修改容易冲突；
- 初学者容易把逻辑、动画和 UI 写在同一个脚本；
- 脉冲生命周期、Tick 批次和运行期移动仍需要自行设计；
- AI 生成代码可能引用旧版 Godot API；
- 如果直接使用帧时间驱动玩法，可能在不同设备上产生不一致结果。

### 实现玩法的困难

Godot 本身可以实现全部玩法。真正困难的不是引擎能力，而是：

- 普通光线的脉冲结算、显示和瞬时状态清理；
- 光粒的固定 Tick 激活窗口和无轨迹表现；
- 运行期移动配额、请求队列和占用原子更新；
- 机关配置锁定和阶段状态；
- 控制机关瞬时/随动与锁存状态的生命周期；
- 独立水晶保持、复合条件匹配和水晶组固定窗口；
- 特殊持续光线的重新计算；
- 同时和顺序事件；
- 反馈循环终止。

## 4. 编程语言规范

采用静态类型 GDScript，不使用 C#，不混用两套语言。

### 4.1 基本要求

- 公共函数必须写参数类型；
- 公共函数必须写返回类型；
- 重要局部变量尽量写类型；
- 公共枚举统一集中定义；
- 核心状态不使用结构随意变化的 Dictionary；
- 处理重要警告；
- 代码提交前必须能正常运行；
- AI 生成代码必须由提交者理解。

示例：

```gdscript
func get_next_cell(
    cell: Vector2i,
    direction: Vector2i
) -> Vector2i:
    return cell + direction
```

### 4.2 中文注释规范

每个 GDScript 模块必须在文件顶部使用中文注释说明：

- 模块职责；
- 在当前系统中的位置；
- 主要依赖；
- 明确不负责的内容。

每个函数必须使用中文 `##` 文档注释，并根据实际情况说明：

- 函数用途；
- 输入参数；
- 返回值；
- 修改的运行状态；
- 关键副作用；
- 停止条件或边界条件。

以下不直观逻辑必须添加必要的行内中文注释：

- Tick 批量结算；
- 脉冲结束清理；
- 瞬时状态到期；
- 锁存状态保持；
- 运行期移动次数扣除；
- 占用表原子更新；
- 方向映射；
- 坐标转换；
- 重置流程。

禁止使用没有信息价值的逐行复述，例如“给变量赋值”“执行循环”“返回结果”。

修改函数职责、参数、返回值或副作用时，必须同步更新注释。已经通过测试的旧函数不要求只为补注释而单独重写；后续任务修改到该函数时补齐。

### 4.3 不采用 C# 的原因

C# 可以实现全部玩法，但会增加：

- .NET 版本 Godot 环境；
- 新语言学习；
- 构建和导出问题；
- AI 排错范围；
- 团队沟通成本。

对于当前规模，收益不足以抵消额外难度。

## 5. 地图、坐标与机关占用方案

采用：

> `TileMapLayer` 管理静态地图，`Vector2i` 负责格子坐标、方向与传播计算，轻量机关占用表负责多格机关和动态机关查询。

不再预先开发完整的 `GridModel / GridService` 框架。

### 5.1 TileMapLayer 负责

- 地面；
- 墙体；
- 装饰；
- 可放置区域显示；
- 静态地图范围；
- 可消除墙标记与基础墙体查询；
- 世界坐标与格子坐标转换；
- 静态图块的自定义数据。

推荐在 TileSet 自定义数据中保存：

```text
blocks_light
placeable
particle_passable
removable_wall
terrain_type
```

示例：

```gdscript
func world_to_cell(world_position: Vector2) -> Vector2i:
    var local_position: Vector2 = terrain_layer.to_local(world_position)
    return terrain_layer.local_to_map(local_position)

func cell_to_world(cell: Vector2i) -> Vector2:
    return terrain_layer.to_global(
        terrain_layer.map_to_local(cell)
    )
```

### 5.2 Vector2i 负责坐标与方向计算

所有光的逻辑位置使用 `Vector2i`。

八个合法方向统一定义为常量：

```gdscript
const DIR_UP := Vector2i(0, -1)
const DIR_UP_RIGHT := Vector2i(1, -1)
const DIR_RIGHT := Vector2i(1, 0)
const DIR_DOWN_RIGHT := Vector2i(1, 1)
const DIR_DOWN := Vector2i(0, 1)
const DIR_DOWN_LEFT := Vector2i(-1, 1)
const DIR_LEFT := Vector2i(-1, 0)
const DIR_UP_LEFT := Vector2i(-1, -1)
```

下一格直接计算：

```gdscript
var next_cell: Vector2i = current_cell + direction
```

镜面反射也使用向量分量计算或固定映射表。

示例：

```gdscript
func reflect_horizontal(direction: Vector2i) -> Vector2i:
    return Vector2i(direction.x, -direction.y)

func reflect_vertical(direction: Vector2i) -> Vector2i:
    return Vector2i(-direction.x, direction.y)

func reflect_slash(direction: Vector2i) -> Vector2i:
    return Vector2i(-direction.y, -direction.x)

func reflect_backslash(direction: Vector2i) -> Vector2i:
    return Vector2i(direction.y, direction.x)
```

反射前仍然必须判断：

- 是否从合法方向进入；
- 是否与镜面平行；
- 是否撞到长平面镜短边；
- 是否被镜框阻挡。

向量计算只负责得到方向结果，不负责自动判断机关规则。

### 5.3 斜向墙角判断

斜向传播时，检查两个相邻正交格：

```gdscript
func is_diagonal(direction: Vector2i) -> bool:
    return direction.x != 0 and direction.y != 0

func is_diagonal_blocked(
    cell: Vector2i,
    direction: Vector2i
) -> bool:
    if not is_diagonal(direction):
        return false

    var horizontal_cell := cell + Vector2i(direction.x, 0)
    var vertical_cell := cell + Vector2i(0, direction.y)

    return (
        is_cell_blocked(horizontal_cell)
        or is_cell_blocked(vertical_cell)
    )
```

这样可以阻止光从两个墙角之间斜向穿过。

### 5.4 轻量机关占用表

`TileMapLayer` 不单独承担动态机关和多格机关状态。

当前关卡至少保留两个简单记录：

```gdscript
# 格子坐标 → 机关对象或机关 ID
var mechanism_at: Dictionary = {}

# 机关 ID → 该机关占用的全部格子
var occupied_cells_by_id: Dictionary = {}
```

概念示例：

```text
mechanism_at[(4, 3)] = mirror_a
mechanism_at[(5, 3)] = mirror_a

occupied_cells_by_id["mirror_a"] = [
    (4, 3),
    (5, 3)
]
```

这些数据可以由 `PlacementController` 管理，也可以在项目早期直接由 `LevelController` 持有。

首版不要求为它单独建立大型通用框架。

### 5.5 多格机关

两格镜面、三格分光器和四格 T 型分光器必须保存：

- 唯一机关 ID；
- 锚点；
- 朝向或旋转状态；
- 完整占用格列表；
- 机关运行状态。

例如：

```text
mechanism_id: mirror_a
anchor: (4, 3)
orientation: horizontal
occupied_cells:
- (4, 3)
- (5, 3)
```

放置流程：

1. 根据锚点和朝向计算全部占用格；
2. 检查所有格子是否在地图范围内；
3. 检查 TileMapLayer 是否允许放置；
4. 检查占用表中是否已经存在机关；
5. 全部合法后一次性登记全部格子；
6. 创建或显示机关场景。

删除或旋转时，必须先清除旧占用，再登记新占用。

### 5.6 动态机关状态

以下状态不写入 TileMapLayer 作为唯一事实来源：

- 门是否打开；
- 镜面处于哪个方向；
- 二极管是否有信号；
- 锁存是否已经触发；
- 次级发射器是否激活；
- 控制连接目标。

这些状态由机关对象或控制系统保存。

例如：

```text
door_a.is_open = true
mirror_b.state = STATE_B
photodiode_c.has_signal = true
```

TileMapLayer、Sprite 或机关场景只根据状态更新显示。

### 5.7 为什么不能只依赖 TileMapLayer

只使用 TileMapLayer 会遇到：

- 多格图块无法自然表示同一个机关整体；
- 删除或旋转时难以同步清理全部格子；
- 动态门和电动镜面的运行状态难以管理；
- 光电二极管和控制目标关系无法只靠图块表达；
- 运行时图块更新与逻辑处理时机可能不同；
- 测试传播规则时必须加载完整地图和场景。

因此本项目采用的不是“只用 TileMapLayer”，而是：

```text
TileMapLayer：静态地图与视觉基础
Vector2i：坐标、方向和传播计算
机关占用表：多格机关与格子查询
机关对象：动态状态
```

### 5.8 实现难度

该方案比完整的 `GridModel / GridService` 更容易开始。

首阶段只需要完成：

1. TileMapLayer 坐标转换；
2. 静态墙体和可放置区域查询；
3. 单格机关占用；
4. 多格机关占用；
5. 放置、旋转和删除；
6. 根据格子查询机关。

如果后期占用和查询代码明显增多，再将这些字典和函数提取为独立类，不需要在项目开始时提前搭建复杂框架。

### 主要风险

- TileMapLayer 与机关占用表坐标不一致；
- 旋转、删除或运行期移动后旧占用没有清除；
- 动态机关画面和逻辑状态不同步；
- `Vector2i` 方向被写入非法值，如 `(2, 0)`；
- 传播模块绕过统一查询接口直接读取场景节点。

为避免非法方向，应统一使用八个方向常量，并在调试版本中检查：

```gdscript
func is_valid_direction(direction: Vector2i) -> bool:
    return (
        direction != Vector2i.ZERO
        and abs(direction.x) <= 1
        and abs(direction.y) <= 1
    )
```

## 6. 光传播方案

采用：

> 离散格子逻辑模拟 + 整数 Tick 结算 + 视觉事件播放。

不使用物理碰撞、Tween 或真实帧时间作为核心玩法判定。游戏中所谓“碰撞”实际是根据 `Vector2i` 格子坐标、TileMapLayer 数据和机关占用表进行规则查询。

### 6.1 固定处理顺序

```text
进入格子
→ 检查边界和阻挡
→ 处理机关
→ 处理水晶、检测器或二极管
→ 校验水晶复合条件并更新独立水晶或组进度
→ 记录控制机关激活模式和到期 Tick
→ 生成视觉事件
→ 安排下一步传播
```

同一 Tick 的传播事件必须先收集并批量处理，再提交控制状态和机关移动。

### 6.2 普通脉冲光线

普通主发射源默认使用脉冲光线。

一次脉冲流程：

```text
读取当前稳定布局快照
→ 计算完整路径和逻辑到达 Tick
→ 结算机关、水晶条件、组进度和控制信号
→ 开始脉冲显示窗口
→ 默认约 1 秒后结束窗口
→ 清除路径视觉和瞬时/随动控制状态
→ 保留锁存控制状态、普通独立水晶和已完成水晶组
→ 处理到期但未完成的同时组或顺序组
→ 检查通关
→ 进入移动窗口或等待下一次发射
```

技术要求：

- 光线路径不是永久场景状态；
- 普通脉冲结束后，机关移动不会修改已经结束的路径；
- 新布局只有在下一次发射时参与新的脉冲计算；
- 约 1 秒必须由固定 Tick 数或统一脉冲结束事件控制；
- 不能依赖 `_process(delta)` 累积误差决定通关；
- 视觉淡出可以使用 Tween，但 Tween 完成不能作为唯一逻辑依据。

### 6.3 光粒

光粒使用离散 Tick 逐格传播。

技术要求：

- 只显示当前活动光粒；
- 不在已走过的格子留下持续逻辑轨迹；
- 可选短暂残影只属于视觉层；
- 光粒触发瞬时/随动控制目标后登记统一到期 Tick；
- 光粒合法命中普通独立水晶后保持到重置；
- 光粒命中同时组或顺序组时更新对应固定窗口和组进度；
- 锁存控制目标不登记自动到期；
- 机关移动只影响提交后尚未处理的传播事件；
- 已完成的路径不回滚、不重新触发。

### 6.4 特殊持续光线

持续光线只用于明确标记的特殊光源。

技术要求：

- 单独标记光源是否为持续类型；
- 有效信号存在时保持路径；
- 信号、机关或墙体状态变化后全量重新计算；
- 状态解除或重置时清除；
- 不与普通主发射源的脉冲逻辑混用；
- 首版不实现局部依赖图和增量重算。

### 6.5 逻辑与画面分离

逻辑层负责：

- 光进入哪个格子；
- 什么时候进入；
- 是否被阻挡；
- 方向是否改变；
- 是否分光；
- 是否触发目标；
- 水晶复合条件、组进度以及控制激活模式和到期时间；
- 是否扣除运行期移动次数；
- 是否改变机关状态。

画面层负责：

- 光粒移动动画；
- 脉冲光线路径与约 1 秒淡出；
- 可选短残影；
- 镜面反射效果；
- 门开关动画；
- 镜面转动；
- 水晶反馈；
- 剩余移动次数提示；
- 声音。

画面卡顿不能改变玩法结果。

### 6.6 不采用物理碰撞法的原因

使用 Area2D、碰撞体、Timer 或 Tween 直接驱动规则虽然容易原型化，但很难稳定实现：

- 分光；
- 同时水晶；
- 顺序水晶；
- 脉冲结束统一清理；
- 固定 Tick 激活窗口；
- 动态门；
- 电动镜面；
- 次级发射器；
- 锁存与随动；
- 运行期移动原子提交。

### 6.7 物理节点的允许用途

`Area2D`、`CollisionShape2D` 或鼠标命中测试可以用于：

- 判断玩家点击了哪个机关；
- 提供拖拽范围或悬停反馈；
- 处理不影响玩法结果的界面交互。

`Timer` 和 Tween 可以用于视觉播放，但不能作为唯一事实来源。

这些节点不能作为光是否命中墙体、镜面、转换器、水晶或检测器的唯一依据。核心结果必须来自网格、事件队列和机关查询接口。

## 7. 逻辑时间与生命周期

使用整数 Tick 管理传播先后、状态到期和移动提交。

### 7.1 建议规则

- 光线直向经过一格：增加固定 Tick；
- 光线斜向经过一格：增加更长距离对应 Tick；
- 光粒根据速度档位增加不同 Tick；
- 同一 Tick 的事件必须批量处理；
- 同一 Tick 到达视为同时；
- 控制状态在当前批次结束后统一更新；
- 玩家移动请求在安全批次边界统一更新；
- 同一批次中所有光事件必须看到同一份机关占用快照；
- 普通光线脉冲具有统一结束 Tick；
- 控制机关的瞬时激活具有统一保持 Tick 数；
- 同时组和顺序组具有统一固定完成窗口，默认从首个合法成员触发时开始且不刷新；
- 普通独立水晶不设置自动到期 Tick；
- 锁存控制状态不设置自动到期 Tick。

### 7.2 推荐常量

概念上至少使用：

```text
RAY_PULSE_HOLD_TICKS
CONTROL_MOMENTARY_HOLD_TICKS
CRYSTAL_GROUP_WINDOW_TICKS
```

这些窗口默认都映射到视觉上的约 1 秒。实际 Tick 数由统一逻辑步长决定，不允许每个目标各自使用不同浮点倒计时。水晶组可以由关卡显式覆盖窗口，但同一组必须共用一个值。

### 7.3 状态与进度记录

瞬时/随动控制激活至少需要保存：

```text
target_id
activated_tick
expires_tick
source_id
```

锁存控制激活至少需要保存：

```text
target_id
latched_tick
source_id
```

普通独立水晶至少需要保存：

```text
crystal_id
is_lit
completed_tick
source_id
```

同时组或顺序组至少需要保存：

```text
group_id
group_rule
started_tick
expires_tick
lit_member_ids
next_sequence_index
is_completed
```

控制状态到期、水晶组窗口到期和组完成必须在批次边界统一结算，避免同一 Tick 中部分事件看到旧状态、部分事件看到新状态。普通独立水晶一旦合法点亮，不登记自动到期事件。

### 7.4 作用

统一 Tick 用于实现：

- 脉冲光线结束；
- 控制机关瞬时激活窗口；
- 普通独立水晶保持；
- 顺序水晶固定组窗口；
- 同时水晶固定组窗口；
- 分光后的先后；
- 光粒和光线混合；
- 次级发射器；
- 动态机关更新；
- 运行期移动次数提交；
- 墙体消除器切换墙体阻挡状态。

### 7.5 主要困难

- 同一 Tick 事件不能逐个即时修改全局状态；
- 到期恢复和新激活可能发生在同一批次；
- 需要先收集，再批量结算；
- 普通脉冲和特殊持续光线必须明确区分；
- 动态状态变化后可能需要开启新的计算阶段。

## 8. 光状态、控制激活模式与水晶条件

采用一个受限制的 `LightState`，避免两个独立状态类增加开发难度。

概念字段：

```text
mode
cell
direction
speed_level
ray_color
source_id
logical_tick
pulse_id
source_behavior
```

规则：

- 光粒模式下 `ray_color` 必须为 `NONE`；
- 光线模式下颜色必须是 `WHITE / RED / GREEN / BLUE`；
- 光粒使用速度字段；
- 普通光线使用 `pulse_id` 标识所属脉冲；
- 特殊持续光线使用明确的 `source_behavior`；
- 通过工厂函数创建光粒和光线；
- 传播前运行状态合法性检查；
- 禁止外部脚本随意修改内部字段。

示例结构：

```gdscript
class_name LightState
extends RefCounted

var mode: LightMode
var cell: Vector2i
var direction: Vector2i
var speed_level: SpeedLevel
var ray_color: RayColor
var source_id: StringName
var logical_tick: int
var pulse_id: int
var source_behavior: SourceBehavior
```

### 8.1 控制激活模式

统一枚举：

```gdscript
enum ActivationMode {
    MOMENTARY,
    LATCHED,
}
```

规则：

- `MOMENTARY` 必须登记到期事件；
- `LATCHED` 保持到重置本次运行；
- 该枚举只用于光电二极管和受控机关，不用于决定水晶是否保持；
- 激活模式属于控制逻辑配置，不由视觉节点决定；
- 运行阶段禁止玩家修改激活模式。

### 8.2 水晶条件模型

水晶使用可组合字段，而不是互斥的 `CrystalType`：

```text
crystal_id
required_light_form
required_ray_color
group_rule
group_id
sequence_index
completion_window_ticks
is_required
is_lit
```

推荐枚举：

```gdscript
enum CrystalGroupRule {
    NONE,
    SIMULTANEOUS,
    SEQUENCE,
}
```

规则：

- 所有已启用条件使用“并且”关系；
- `group_rule = NONE` 的普通独立水晶合法命中后保持到重置，不登记自动到期；
- 同时组和顺序组从首个合法成员触发时开始固定窗口，后续触发不刷新窗口；
- 未完成组到期时整组恢复未点亮；
- 组完成后保持到重置；
- 光粒没有颜色，遇到具体颜色要求时匹配失败；
- 同一颗水晶不能同时属于同时组和顺序组；
- 水晶视觉状态至少区分未点亮半透明与点亮完全不透明。

### 8.3 工厂函数

```gdscript
static func create_particle(...) -> LightState:
    # ray_color 必须为 NONE。
    pass

static func create_pulse_ray(...) -> LightState:
    # 必须有合法颜色和 pulse_id。
    pass

static func create_continuous_ray(...) -> LightState:
    # 仅允许特殊持续光源调用。
    pass
```

### 8.4 合法性检查

```gdscript
func is_valid() -> bool:
    if mode == LightMode.PARTICLE:
        return ray_color == RayColor.NONE
    return ray_color != RayColor.NONE
```

还应检查：

- `direction` 是否为八个合法方向之一；
- 普通脉冲光线是否拥有合法 `pulse_id`；
- 特殊持续光线是否来自允许的光源；
- 光粒是否错误携带颜色。

## 9. 推荐模块划分

```text
LevelController
├─ RunStateController
├─ TerrainLayer（TileMapLayer）
├─ PlacementController / OccupancyRegistry
├─ PropagationSimulator
├─ ObjectiveController
├─ ControlSignalController
└─ VisualController
```

当前项目仍然按照实际需求逐步拆分，不要求一次性创建全部模块。

### 9.1 LevelController

负责：

- 初始化关卡；
- 读取关卡元信息；
- 连接各模块；
- 开始普通光线脉冲或光粒传播；
- 重置本次运行；
- 重置整个关卡；
- 接收通关结果；
- 协调 RunStateController、传播、放置和目标模块。

不负责：

- 具体镜面反射；
- 具体水晶规则；
- 具体画面动画。

### 9.2 RunStateController

负责管理关卡状态：

```text
SETUP
→ RUNNING
→ SETTLING
→ MOVE_WINDOW
→ RUNNING / COMPLETED / SETUP
```

其中：

- `RUNNING` 可以是普通光线脉冲或光粒传播；
- `SETTLING` 负责控制信号、状态到期和队列清理；
- `MOVE_WINDOW` 允许在配置锁定状态下进行有限移动或再次发射。

具体职责：

- 第一次发射后锁定玩家机关配置；
- 保存 `runtime_move_limit` 与 `runtime_moves_used`；
- 判断当前操作是否允许；
- 判断普通光线脉冲是否正在计算；
- 判断移动请求何时可以提交；
- 处理重置并恢复移动次数；
- 判断传播队列、移动队列和控制信号是否稳定；
- 在运行结束或重置时解除配置锁定；
- 防止界面层直接修改运行状态。

不负责具体光传播、占用计算和机关规则。

### 9.3 TerrainLayer

使用 Godot 官方 `TileMapLayer`，负责：

- 静态地图显示；
- 墙体、可放置区域和可消除墙；
- TileSet 自定义数据；
- 根据临时失效表返回墙体当前是否阻挡；
- 世界坐标与格子坐标转换。

### 9.4 PlacementController / OccupancyRegistry

负责：

- 布置阶段的机关放置、移动、旋转和删除；
- 运行阶段的有限移动请求；
- 机关配置锁定状态检查；
- 单格与多格机关占用；
- `mechanism_at` 查询；
- `occupied_cells_by_id` 维护；
- 放置合法性；
- 固定机关和玩家机关登记；
- 墙体消除器与被临时关闭墙体的对应关系。

只有移动成功提交后才通知 RunStateController 扣除一次移动次数。该模块不承担光传播、水晶和控制信号逻辑。

### 9.5 PropagationSimulator

负责：

- 光粒传播；
- 普通脉冲光线传播；
- 特殊持续光线传播；
- Tick 队列；
- 脉冲 ID 和结束事件；
- 八方向反射；
- 斜向墙角判断；
- 分光；
- 滤光；
- 形式转换；
- 循环终止；
- 产生传播事件；
- 特殊持续光线在机关或墙体状态变化后的全量重算；
- 保证普通脉冲结束后不会自动随布局重算；
- 保证光粒不会因后续移动回溯已经完成的路径。

### 9.6 ObjectiveController

负责：

- 水晶光形式、颜色等复合条件匹配；
- 普通独立水晶的保持状态；
- 同时组和顺序组；
- 固定组窗口、组到期和组重置；
- 水晶点亮/未点亮状态；
- 可选水晶与必需水晶；
- 全部目标完成判断。

不负责光电二极管和受控机关的 `MOMENTARY / LATCHED` 控制状态。

### 9.7 ControlSignalController

负责：

- 光电二极管；
- 控制连接；
- 瞬时/随动；
- 锁存；
- 电控门；
- 电动镜面；
- 次级脉冲发射器；
- 特殊持续发射器；
- 状态批量更新；
- 到期恢复；
- 重复状态检测。

### 9.8 VisualController

负责：

- 光粒动画；
- 普通光线路径约 1 秒显示与淡出；
- 特殊持续光线路径；
- 门开关；
- 镜面旋转；
- 水晶未点亮半透明、临时点亮和完成点亮反馈；
- 控制机关瞬时与锁存状态差异；
- 剩余运行期移动次数；
- 声音；
- 调试显示。

不直接决定玩法结果。

## 10. 全局单例规范

只把真正跨场景的服务设为 Autoload。

建议：

- `GameFlow`；
- `SaveManager`；
- `AchievementManager`；
- `AudioManager`，有需要时再加入。

不要设为 Autoload：

- `RunStateController`；
- `PlacementController`；
- `OccupancyRegistry`；
- `PropagationSimulator`；
- `ObjectiveController`；
- `ControlSignalController`。

禁止建立包含全部逻辑的巨大 `GameManager`。

## 11. 机关配置方式

机关和水晶采用：

> 独立场景 + Inspector 导出属性。

示例属性：

```gdscript
@export var mechanism_id: StringName
@export var input_direction: Vector2i
@export var rotation_state: int
@export var activation_mode: ActivationMode
@export var target_ids: Array[StringName]
@export var player_owned: bool = false
@export var movable_during_run: bool = false
@export var configuration_locked: bool = false
```

水晶示例：

```gdscript
@export var crystal_id: StringName
@export var required_light_form: LightFormRequirement
@export var required_ray_color: RayColorRequirement
@export var group_rule: CrystalGroupRule
@export var group_id: StringName
@export var sequence_index: int
@export var completion_window_ticks: int
@export var is_required: bool = true
```

未点亮和点亮透明度应集中定义，例如：

```gdscript
const UNLIT_ALPHA: float = 0.35
const LIT_ALPHA: float = 1.0
```

### 优点

- 关卡成员可以直接配置；
- 不需要先开发关卡编辑器；
- 比复杂 Resource 嵌套容易理解；
- 适合当前项目规模。

### 缺点

- 配置分散在场景节点；
- 场景文件改动较多；
- 多人同时改同一场景容易冲突。

## 12. 关卡数据

使用简单的 `LevelData.tres` 保存：

- 关卡 ID；
- 关卡名称；
- 初始光形式；
- 普通主光源行为；
- 可用机关；
- 机关数量；
- `runtime_move_limit`；
- 光粒瞬时激活 Tick 窗口；
- 是否允许特殊持续光线；
- 下一关 ID；
- 教学提示；
- 章节信息。

推荐约束：

- 普通主发射源默认是脉冲光线；
- 静态关卡的 `runtime_move_limit` 为 `0`；
- 动态教学关卡通常为 `1`；
- 普通复杂动态关卡通常不超过 `2`；
- 特殊关卡才允许 `3`；
- Tick 窗口优先使用项目统一默认值，不为每关随意设置。

不为每个机关建立复杂 Resource 层级。

## 13. 机关连接与关卡合法性

光电二极管和被控机关使用唯一 ID 连接。

关卡加载时建立：

```text
机关 ID → 机关对象
```

规则：

- 一个二极管可控制多个机关；
- 一个受控机关首版只接受一个信号来源；
- ID 必须唯一；
- 目标 ID 必须存在。

启动关卡时应检查：

- 重复 ID；
- 缺失目标 ID；
- 多格机关重叠；
- 机关越界；
- 水晶 ID 重复；
- 水晶具体颜色要求与光粒形式要求互相矛盾；
- 同时组或顺序组缺少 `group_id`；
- 顺序水晶编号不连续或重复；
- 同一水晶同时配置多个组规则；
- 同组水晶的完成窗口不一致；
- 分光器端口被阻挡；
- 可消除墙缺少对应标记；
- 墙体消除器初始位置非法；
- 玩家机关的运行期移动权限配置错误；
- `runtime_move_limit` 小于 `0` 或超过当前版本允许上限；
- 普通主发射源被错误配置为持续光线；
- 瞬时/随动控制目标缺少统一到期窗口；
- 锁存控制目标被错误登记自动到期；
- 普通独立水晶被错误登记自动到期；
- 特殊持续光源缺少明确标记；
- 关卡初始状态非法。

## 14. 模块通信

采用：

- 需要立即得到返回结果：普通函数调用；
- 某件事已经发生：Godot Signal；
- 跨场景长期状态：少量 Autoload。

避免：

- 大量 `get_parent().get_node()`；
- 任意模块直接修改其他模块内部变量；
- 全局万能 EventBus；
- 机关直接负责通关、存档和切场景。

## 15. 状态生命周期、动态控制与重新计算

控制状态、到期状态和移动请求在逻辑批次边界统一应用。

普通脉冲流程：

```text
读取稳定布局
→ 计算脉冲路径
→ 收集水晶条件命中、组进度与二极管信号
→ 批量提交水晶和控制状态
→ 显示路径约 1 秒
→ 脉冲结束
→ 批量恢复瞬时/随动控制状态
→ 保留锁存控制状态、普通独立水晶和已完成水晶组
→ 处理到期但未完成的水晶组
→ 检查通关
→ 进入移动窗口或等待下一次发射
```

光粒批次流程：

```text
处理同一 Tick 的光粒事件
→ 收集新激活、到期状态和玩家移动请求
→ 结束当前批次
→ 先结算到期状态
→ 校验并提交合法机关移动
→ 成功移动时扣除次数
→ 更新门、镜面、次级发射器和临时墙体状态
→ 安排下一 Tick
```

特殊持续光线流程：

```text
状态或布局变化
→ 清除旧的特殊持续路径
→ 保留当前锁存与随动状态快照
→ 从全部活动特殊持续光源全量重新计算
→ 生成新路径
```

普通脉冲光线不因脉冲结束后的机关移动自动重算；玩家需要再次发射。

### 15.1 控制状态与水晶状态

瞬时/随动控制状态：

- 必须保存明确的到期 Tick 或脉冲 ID；
- 到期后在批次边界恢复；
- 恢复操作必须幂等；
- 重复激活可以按统一规则刷新到期时间。

锁存控制状态：

- 不登记自动到期；
- 重复信号不重复执行一次性副作用；
- 只在重置本次运行时清除。

普通独立水晶：

- 合法命中后保持点亮；
- 不随脉冲结束或光粒离开恢复；
- 只在重置本次运行时清除；
- 未点亮时半透明，点亮时完全不透明。

同时组和顺序组：

- 以组为单位保存固定开始 Tick、到期 Tick、临时点亮成员和进度；
- 第一颗合法成员开始窗口，后续合法触发不刷新窗口；
- 未完成组到期时整组幂等恢复；
- 组完成后取消自动到期并保持到重置；
- 顺序错误时立即清除整组临时状态。

### 15.2 重复状态检测

为防止特殊持续光线和随动机关无限振荡，记录全局受控机关状态。

例如：

```text
door_a=open
mirror_b=state_1
emitter_c=continuous_active
latched_diode_d=true
```

如果同一状态组合再次出现，并且仍会继续生成新事件，停止本次运行。

普通脉冲光线结束后没有活动路径，不需要因为布局保持不变而持续检测。

### 15.3 主要困难

这是项目风险较高的技术部分：

- 控制机关瞬时状态恢复时机不一致；
- 普通独立水晶被错误随脉冲清除；
- 水晶组窗口被错误刷新或跨组共享；
- 普通脉冲被错误保留为持续路径；
- 锁存控制状态被误清除；
- 同一 Tick 中新激活和旧状态到期冲突；
- 特殊持续光线可能反复重算；
- 次级发射器可能引发新一轮传播；
- 机关可能形成反馈循环。

### 15.4 简化要求

- 普通主发射源只使用脉冲光线；
- 一个受控机关只有一个信号来源；
- 控制激活窗口和水晶组窗口分别使用统一常量；
- 普通独立水晶先实现保持到重置，再实现同时组和顺序组；
- 控制系统先实现锁存，再实现少量随动关卡；
- 次级光粒和次级脉冲光线发射器采用上升沿单次发射；
- 状态在批次结束后统一改变；
- 特殊持续光源数量保持很少；
- 检测到重复状态后停止运行。

## 16. 运行阶段编辑、移动配额与墙体消除器

### 16.1 操作权限

运行阶段使用白名单控制操作。

允许：

- 选择玩家自己放置且允许运行期移动的机关；
- 在剩余移动次数大于 `0` 时提交合法移动请求；
- 移动允许运行期移动的墙体消除器；
- 再次发射普通脉冲；
- 重置本次运行。

禁止：

- 新增或回收机关；
- 删除机关；
- 旋转机关；
- 修改输入端、输出方向、滤光颜色、检测条件、激活模式或转换模式；
- 移动关卡预置机关、水晶、检测器和受控机关；
- 在普通脉冲正在计算和结算时提交移动；
- 在移动次数耗尽后继续移动。

操作权限必须由 `RunStateController` 和 `PlacementController` 共同检查，不能只依赖按钮是否隐藏。

### 16.2 运行期移动配额

`RunStateController` 至少保存：

```text
runtime_move_limit
runtime_moves_used
```

剩余次数：

```text
runtime_moves_remaining =
    runtime_move_limit - runtime_moves_used
```

规则：

- 只有原子提交成功后才增加 `runtime_moves_used`；
- 非法目标、取消拖拽和返回原位置不扣除；
- 重置本次运行时恢复为 `0`；
- 不能减成负数；
- UI 只能读取和显示，不能自行修改次数；
- 关卡默认上限建议为 `0—2`，特殊关卡最多 `3`。

### 16.3 移动请求队列

移动操作不能在鼠标拖拽过程中直接改写核心占用表。

推荐流程：

```text
玩家选择目标格
→ 检查权限、剩余次数、范围和占用
→ 创建 MoveRequest
→ 当前 Tick 或脉冲批次处理完成
→ 再次校验目标格和剩余次数
→ 原子性清除旧占用并登记新占用
→ 增加 runtime_moves_used
→ 发出 mechanism_moved 事件
```

概念结构：

```text
mechanism_id
from_anchor
to_anchor
requested_tick
request_order
```

同一 Tick 存在多个请求时，按照确定顺序处理；后处理请求若与已提交的新占用冲突，则拒绝并给出反馈，不扣除次数。

### 16.4 光粒处理

- 光粒事件使用移动提交后的新占用继续传播；
- 已经完成的 Tick 不回滚；
- 已经经过某格的光粒不会因为机关后来移动到该格而重新处理；
- 移动提交前已排入同一 Tick 的其他事件继续使用该批次开始时的占用快照；
- 光粒视觉不留下持续路径；
- 光粒触发的瞬时/随动控制目标在统一 Tick 窗口结束后恢复；普通独立水晶和水晶组按 ObjectiveController 规则处理。

### 16.5 普通脉冲光线处理

- 脉冲计算和结算期间拒绝移动提交；
- 脉冲结束后可以进入移动窗口；
- 移动只影响下一次发射；
- 不保留旧脉冲路径；
- 不在每次拖动后自动重算普通光线。

### 16.6 特殊持续光线处理

首版采用确定性优先的全量重算：

1. 机关移动或墙体阻挡状态改变；
2. 清除当前特殊持续光线路径；
3. 保留发射源、锁存状态和当前有效随动状态；
4. 从全部活动特殊持续光线发射源重新计算；
5. 重新生成视觉路径。

暂不实现复杂的局部依赖图和增量重算。

### 16.7 墙体消除器

墙体消除器不直接删除 TileMap 图块。技术上采用“临时失效表”：

```gdscript
# 墙体格坐标 → 当前覆盖它的墙体消除器 ID
var disabled_wall_by_cell: Dictionary[Vector2i, StringName] = {}
```

墙体查询应通过统一接口：

```gdscript
func is_wall_blocking(cell: Vector2i) -> bool:
    if disabled_wall_by_cell.has(cell):
        return false
    return terrain_layer_has_blocking_wall(cell)
```

移动墙体消除器时必须原子性完成：

1. 检查剩余移动次数；
2. 检查新位置是否为 `removable_wall = true`；
3. 移除原墙体格的临时失效记录；
4. 更新道具占用；
5. 写入新墙体格的临时失效记录；
6. 增加 `runtime_moves_used`；
7. 通知后续光粒使用新状态；
8. 下一次普通脉冲使用新墙体状态；
9. 特殊持续光线按需全量重算。

重置整个关卡时清空临时失效表。重置本次运行时保留玩家当前布局与墙体消除器当前位置，但停止传播、清除激活状态、恢复移动次数并解除配置锁定。

### 16.8 运行稳定判定

`RunStateController` 判断一个传播批次稳定时至少检查：

- 当前普通脉冲已经结束；
- 当前 Tick 事件处理完成；
- 到期状态已经结算；
- 移动请求队列为空；
- 待处理控制信号为空；
- 没有待启动次级发射器；
- 没有待执行的特殊持续光线重算。

普通脉冲结束但关卡未完成时，可以进入 `MOVE_WINDOW`，不自动解除配置锁定。

### 16.9 主要风险与简化

风险：

- 移动请求与同 Tick 光事件看到不同布局；
- 成功移动未扣次数或失败移动错误扣次数；
- 多格机关移动后残留旧占用；
- 普通脉冲被错误持续重算；
- 墙体视觉恢复但逻辑仍可穿过；
- 玩家绕过移动次数限制。

简化要求：

- 首版先支持单格机关运行期移动；
- 单格逻辑稳定后再支持多格机关；
- 普通光线只在发射时计算；
- 特殊持续光线使用全量重算；
- 一个墙体消除器同时只对应一格墙；
- 正式关卡限制可移动机关和移动次数；
- 移动冷却、动画和手感只影响表现，不改变逻辑提交顺序。

## 17. 成就系统

成就系统用于在游戏过程中宣讲戴琼海院士等中国科学家及其科研精神。

### 17.1 AchievementManager

`AchievementManager` 作为跨场景 Autoload，负责：

- 接收玩法模块发出的成就事件；
- 判断成就是否已经解锁；
- 保存解锁状态；
- 将新成就加入弹窗队列；
- 通知成就展示页面刷新对应内容；
- 可选地通知科学家档案页面解锁对应内容。

玩法模块只报告事件，例如完成某关、首次使用某机关或完成某种组合目标。玩法模块不能直接创建弹窗，也不能直接写成就存档。

### 17.2 成就数据

建议使用简单的 `AchievementData.tres` 或统一成就数据表，包含：

```text
achievement_id
title
scientist_name
spirit_keyword
short_description
full_description
icon
archive_entry_id
hidden_before_unlock
```

成就数据和科学家档案内容分开保存。弹窗只读取短文本，成就展示页面读取完整成就说明，科学家档案可继续承载更完整人物资料。

### 17.3 AchievementToast UI

右下角成就弹窗独立为 UI 场景，负责：

- 从右下角进入和退出；
- 显示图标、标题、科学家姓名和简短说明；
- 多个成就排队；
- 不暂停游戏；
- 不拦截无关输入；
- 在不同分辨率下保持在安全区域内。

禁止由每个关卡自行制作成就弹窗。

### 17.4 AchievementGallery

主界面新增“成就展示”按钮，进入统一的 `AchievementGallery` 页面。

页面负责：

- 成就列表或网格展示；
- 已解锁与未解锁状态；
- 成就详情；
- 对应科学家和科研精神说明；
- 成就获得条件；
- 可选的分类、完成度和解锁时间；
- 返回主界面。

未解锁成就应支持隐藏描述，避免泄露关卡解法。

`AchievementGallery` 只读取 `AchievementManager` 提供的数据，不直接修改成就存档。

### 17.5 触发规范

成就由明确的玩法事件触发，优先使用 Signal 或由 `LevelController` 上报。

成就判断不得依赖动画是否播放完成，也不得通过查找 UI 节点判断。

### 17.6 存档

`ConfigFile` 需要保存：

- 已解锁成就 ID；
- 已解锁科学家档案 ID；
- 可选的首次解锁时间。

已经解锁的成就再次满足条件时不重复弹出，除非以后单独设计可重复挑战。

### 17.7 内容规范

- 科学家姓名、成果和精神说明必须来自已审核内容；
- 不在代码中散落人物介绍文字；
- 不使用未经确认的科学家名言；
- 成就文本修改应集中在成就数据文件；
- 成就系统不影响主线解锁和光传播判定。

## 18. 存档方案

## 27. 最终技术选择

当前建议确定为：

- Godot 4.6.1 Standard；
- 静态类型 GDScript；
- 每个新建或修改的模块和函数使用有意义的中文注释；
- TileMapLayer 负责静态地图、坐标转换和图块自定义数据；
- Vector2i 负责格子坐标、八方向和反射计算；
- 使用轻量 `mechanism_at` 与 `occupied_cells_by_id` 记录机关占用；
- 动态机关状态保存在机关对象和控制系统中；
- 暂不开发完整的 `GridModel / GridService`，代码增长后再按需提取；
- 离散整数 Tick 传播；
- 普通主发射源使用脉冲光线；
- 普通脉冲路径默认显示约 1 秒后清除；
- 光粒只显示当前粒子，不保留持续轨迹；
- 光电二极管和受控机关使用 `MOMENTARY` 与 `LATCHED` 控制生命周期；
- 瞬时/随动控制状态通过固定 Tick 或脉冲结束事件恢复；
- 锁存控制状态保持到重置本次运行；
- 水晶使用光形式、颜色和组规则的可组合条件；
- 普通独立水晶合法点亮后保持到重置；
- 同时组和顺序组使用从首个合法成员开始且不刷新的固定组窗口；
- 未完成组到期后整组恢复，完成组保持到重置；
- 水晶未点亮使用半透明反馈，点亮使用完全不透明反馈；
- 使用 RunStateController 管理布置、运行、结算、移动窗口和完成状态；
- 第一次发射后锁定玩家机关人工配置；
- 每关通过 `runtime_move_limit` 限制运行期移动；
- 只有成功提交的移动扣除次数；
- 移动请求在 Tick 或脉冲批次结束后原子提交；
- 光粒不回溯；
- 普通脉冲光线只在再次发射时按新布局计算；
- 持续光线仅用于特殊光源，并在布局变化后全量重算；
- 墙体消除器使用临时失效表，不永久删除 TileMap 图块；
- 逻辑与视觉分离；
- 一个受限制的 LightState；
- 机关场景加 Inspector 导出属性；
- 简单 LevelData Resource；
- 普通函数调用加 Signal；
- 少量 Autoload，包括 AchievementManager；
- 状态变化批量应用；
- 重复状态检测；
- 次级光粒和次级脉冲光线发射器使用上升沿单次发射；
- 测试场景和 assert 优先；
- GUT、Docker、CI 和自动导出后置；
- GitHub Desktop、短期任务分支和 Pull Request；
- AI 一次只处理小范围任务；
- 成就弹窗采用统一 AchievementToast UI；
- 主界面提供 AchievementGallery 成就展示入口；
- 成就和科学家档案通过 AchievementManager 解锁并保存。
