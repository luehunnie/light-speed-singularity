## 1. 使用前必须理解的三类内容

### 1.1 玩法事实

玩法事实决定游戏实际如何运行，例如：

- 镜面位于哪个逻辑格；
- 发射器从哪个格子发光；
- 墙体实际阻挡哪个格子；
- 水晶在哪个格子接受光；
- 光线当前朝哪个方向传播。

玩法事实通常使用 `Vector2i` 格坐标保存，不能通过移动一张图片来修改。

### 1.2 视觉资源

视觉资源只决定“显示什么图片”，例如：

- 水晶点亮和未点亮图片；
- 镜面 `/`、`\` 两种图片；
- 道具栏图标；
- 光线 `-`、`|`、`/`、`\` 四种图片。

视觉资源通过 `.tres` 配置。替换视觉资源不会改变玩法规则。

### 1.3 场景布局

场景布局决定 UI 或视觉节点显示在哪里、多大，例如：

- 底部道具栏高度；
- 单个槽位宽高；
- 图标预览区域大小；
- UI 与窗口边缘的距离。

UI 布局可以在 Godot Inspector 中调整，但要遵守 `Container` 自动布局规则。

## 2. 当前可以替换的美术资源

## 2.1 普通水晶

视觉配置资源：

```text
assets/visual_profiles/basic_crystal_visuals.tres
```

当前应包含两个视觉状态：

- 未点亮；
- 已点亮。

### 操作步骤

1. 将新的 PNG 放入项目约定的美术目录。
2. 等待 Godot 完成导入。
3. 在 FileSystem 中打开：

   ```text
   assets/visual_profiles/basic_crystal_visuals.tres
   ```

4. 在 Inspector 中找到未点亮和已点亮状态对应的纹理字段。
5. 分别拖入新图片。
6. 保存资源。
7. 运行原型场景。
8. 检查水晶点亮前后是否正确切换。

### 注意

- 不要修改 `basic_crystal.gd` 来换图片。
- 不要移动 `Artwork` 子节点来改变水晶的玩法位置。
- 图片建议使用透明背景。
- 单格世界物件建议使用 64×64 画布。

---

## 2.2 单格镜面

视觉配置资源：

```text
assets/visual_profiles/single_cell_mirror_visuals.tres
```

当前镜面状态包括：

- `/`：左下到右上；
- `\`：左上到右下；
- `inventory_icon`：底部道具栏图标。

### 世界镜面图片替换

1. 打开：

   ```text
   assets/visual_profiles/single_cell_mirror_visuals.tres
   ```

2. 找到 `/` 和 `\` 对应状态。
3. 将对应 PNG 拖入纹理字段。
4. 保存。
5. 运行场景。
6. 右键切换镜面方向，检查两张图片是否对应正确。

### 道具栏图标替换

在同一个资源中找到：

```text
inventory_icon
```

将正式图标拖入该字段并保存。

显示规则：

```text
inventory_icon 有图片
→ 显示正式图片
→ 隐藏蓝绿色占位符

inventory_icon 为空
→ 隐藏正式图片
→ 保留蓝绿色占位符
```

### 注意

- 道具栏图标不会自动使用世界镜面图片。
- `inventory_icon` 为空是合法配置，不会报缺图警告。
- 不要把 `world_texture` 或 `drag_texture` 当成道具栏图标替代字段。
- 当前图标显示区域约为 44×44 像素。
- 图标源文件建议采用正方形画布，确保缩小到 44×44 时仍清晰。

---

## 2.3 光线路径

视觉配置资源：

```text
assets/visual_profiles/basic_light_segment_visuals.tres
```

四个字段与形态的对应关系：

| 字段 | 视觉形态 | 对应传播方向 |
|---|---|---|
| `horizontal_texture` | `-` | 左、右 |
| `vertical_texture` | `|` | 上、下 |
| `slash_texture` | `/` | 右上、左下 |
| `backslash_texture` | `\` | 右下、左上 |

Godot 2D 坐标的 Y 轴向下，因此：

```text
Vector2i(1, -1)  → /
Vector2i(-1, 1)  → /

Vector2i(1, 1)   → \
Vector2i(-1, -1) → \
```

### 操作步骤

1. 准备四张透明 PNG。
2. 将图片放入项目约定的美术目录。
3. 等待 Godot 导入。
4. 打开：

   ```text
   assets/visual_profiles/basic_light_segment_visuals.tres
   ```

5. 将四张图片分别拖入对应字段。
6. 保存资源。
7. 运行场景并发射光线。
8. 检查水平、垂直和两类斜向显示是否正确。

### 空纹理回退

四个字段可以为空。

```text
对应纹理存在
→ 显示正式光线图片

对应纹理为空
→ 显示原有黄色 64×64 占位块
```

缺少纹理不会产生警告。

### 光线素材制作建议

- 画布：64×64。
- 背景：透明。
- 图案：白色或灰度。
- 线条应经过画布中心。
- 线条两端应接触画布边缘，减少相邻格之间的断缝。
- 不建议分别制作红、绿、蓝三套图片。
- 运行时会使用颜色调制；彩色原图可能与调制颜色相乘后产生偏色。

### 当前限制

当前光路使用“每进入一个格子生成一段视觉”的模型。

镜面格中显示入射方向，反射后的方向从下一个格子开始显示。当前没有半格线段、转角图片或复合光路图片。

## 3. 如何调整世界物件图片的显示大小

## 3.1 当前统一单格视觉区域

单格物件通常使用：

```text
64×64
```

局部坐标范围通常是：

```text
左上：(-32, -32)
右下：(32, 32)
```

涉及的公共视觉场景：

```text
gameplay/visuals/object_visual_view.tscn
```

### 不建议张梓涵直接修改公共场景大小

修改 `object_visual_view.tscn` 会同时影响所有使用该视觉组件的物件，例如：

- 水晶；
- 单格镜面；
- 后续接入的单格机关。

因此，除非项目决定所有单格物件统一变大或变小，否则不要直接修改公共 `Artwork` 的 offsets。

### 推荐方式

1. 美术图片本身使用 64×64 画布。
2. 在画布内控制主体大小和透明留白。
3. 保持 Godot 中的单格视觉边界为 64×64。
4. 通过图片内部构图实现“看起来更大或更小”。

例如：

```text
想让镜面看起来小一些
→ 不改节点大小
→ 在64×64透明画布中缩小镜面主体并增加透明边距
```

这种方式不会破坏：

- 格子对齐；
- 拖拽预览；
- 鼠标命中；
- 占用格；
- 视觉反馈覆盖层。

---

## 3.2 拖拽状态大小

当前镜面拖拽时可能应用轻微缩放，用来表示“正在拿起”。

该缩放属于交互反馈，不建议由美术人员随意修改。若确实需要调整，应由陈俊贤统一修改拖拽视觉配置并重新测试：

- 合法位置反馈；
- 非法位置反馈；
- 鼠标命中；
- 回收；
- 边缘格显示。

---

## 3.3 光线显示大小

光线 `LightSegmentView` 的显示区域为单格 64×64。

不建议改变节点区域大小。正式素材应通过 64×64 透明画布适配。

若修改为大于 64×64，可能产生：

- 覆盖相邻格；
- 光线与镜面、水晶重叠；
- 相邻光段叠加过亮；
- 边界裁切；
- 视觉与传播格不一致。

## 4. 如何调整底部道具栏大小

底部道具栏位于原型场景：

```text
levels/prototypes/core_loop_prototype.tscn
```

主要节点结构类似：

```text
CanvasLayer
└─ InventoryBar
   └─ MarginContainer
      └─ HBoxContainer
         └─ PrototypeTokenSlot
            └─ SlotMargin
               └─ SlotContent
                  ├─ IconStack
                  │  ├─ TokenIcon
                  │  └─ InventoryIcon
                  └─ SlotTexts
                     ├─ NameLabel
                     └─ RemainingLabel
```

## 4.1 调整整个道具栏

选中：

```text
InventoryBar
```

可调整：

- Anchors；
- Offset Left；
- Offset Top；
- Offset Right；
- Offset Bottom；
- Custom Minimum Size。

### 建议

- 继续保持底部锚定。
- 修改高度时优先调整顶部 offset。
- 不要把 UI 改到遮挡主要关卡区域。
- 修改后必须在目标窗口尺寸下运行测试。

---

## 4.2 调整单个道具槽大小

选中：

```text
PrototypeTokenSlot
```

修改：

```text
Custom Minimum Size
```

### 注意 Container 自动布局

`PrototypeTokenSlot` 位于容器中。最终运行时大小可能同时受到以下内容影响：

- `custom_minimum_size`；
- 图标最小尺寸；
- 文本最小尺寸；
- 字体大小；
- `MarginContainer` 边距；
- `HBoxContainer` separation；
- Theme 和 StyleBox。

因此：

```text
Custom Minimum Size
```

只是最小尺寸，不一定等于最终实际尺寸。

---

## 4.3 调整图标区域大小

选中：

```text
IconStack
```

修改：

```text
Custom Minimum Size
```

当前约为：

```text
44×44
```

`TokenIcon` 和 `InventoryIcon` 会填满同一个 `IconStack` 区域。

若改成 56×56，正式图标和占位符会一起变为该显示区域；随后应检查：

- 槽位是否被撑高；
- 文字是否仍能完整显示；
- 图标与文字间距；
- 道具栏是否超出屏幕；
- 鼠标拖拽命中范围。

---

## 4.4 调整图标和文字之间的间距

选中承载二者的：

```text
SlotContent
```

它通常是 `HBoxContainer`。

间距一般来自：

- Theme 的 `separation`；
- 容器主题覆盖；
- 子节点的最小尺寸；
- `SlotMargin` 的内边距。

不要通过拖动 `InventoryIcon` 的 position 制造间距，因为容器会重新布局它。

---

## 5. 如何调整 UI 位置

UI 节点使用 `Control` 布局。

安全调整方式：

1. 选中需要调整的外层 UI 节点。
2. 使用 Layout、Anchors 和 Offsets。
3. 不要直接拖动深层 Container 子节点。
4. 运行游戏检查最终布局。
5. 测试目标分辨率和窗口缩放。

推荐调整层级：

```text
整个道具栏位置
→ 修改 InventoryBar

道具栏内部边距
→ 修改 MarginContainer 或对应主题常量

槽位之间的间距
→ 修改 HBoxContainer separation

单个槽位大小
→ 修改 PrototypeTokenSlot custom_minimum_size

图标显示大小
→ 修改 IconStack custom_minimum_size
```

## 6. 当前不能仅靠拖动修改的世界位置

## 6.1 固定发射器

当前发射器的实际发射位置仍由玩法格坐标决定。

只移动发射器的 `ColorRect` 或图片会造成：

```text
看到的发射器位置
≠
实际发光的格子
```

因此当前不要仅通过拖动视觉节点修改发射器位置。

---

## 6.2 普通墙

当前墙体阻挡事实仍由逻辑格集合管理。

只移动墙的图片会造成：

```text
看到的墙
≠
真正阻挡光线的墙
```

当前不要仅移动墙体占位节点。

---

## 6.3 固定水晶

水晶视觉已经资源化，但固定水晶的统一关卡编辑工作流尚未完全完成。

不要只移动 `Artwork` 子节点。若临时调整水晶，应由陈俊贤确认场景节点位置和玩法格位置是否同步。

---

## 6.4 光线路径

光线路径由运行时传播逻辑自动生成。

张梓涵只能替换四类光线纹理，不能在关卡场景中手工移动每一段光线。

---

## 6.5 可放置镜面

可放置镜面的世界位置由玩家拖拽和放置系统管理。

关卡设计人员不应通过修改镜面图片的 position 来预设玩家最终摆放位置。

道具栏中提供的镜面种类和数量，未来应通过关卡库存配置管理。

## 7. 下一阶段完成后可以执行的操作

完成关卡静态布局与合法区域编辑阶段后，计划支持：

```text
LegalAreaLayer
→ 绘制地图合法区域和不规则地图形状

WallLayer
→ 绘制普通静态墙

FixedObjects
→ 放置发射器、水晶等固定关卡物件

LevelObjectRegistry
→ 自动收集、校验越界、重叠和数量
```

届时张梓涵的理想流程是：

1. 在 `LegalAreaLayer` 上绘制关卡形状。
2. 在 `WallLayer` 上绘制墙体。
3. 将固定发射器、水晶拖入关卡。
4. 修改物件的逻辑 `Cell`，而不是移动内部图片。
5. 运行校验。
6. 处理越界、重叠或重复发射器错误。
7. 启动关卡测试。

在该阶段完成之前，不要宣称固定物件的位置已经可以完全通过编辑器安全修改。

## 8. 美术资源导入建议

## 8.1 世界单格物件

推荐：

```text
画布：64×64
背景：透明
格式：PNG
```

保持主体位于画布中心，并使用透明留白控制视觉大小。

## 8.2 道具栏图标

推荐使用正方形透明 PNG。

当前显示区域约为：

```text
44×44
```

源文件可使用：

- 44×44；
- 88×88；
- 其他能在缩放后保持像素清晰的正方形尺寸。

使用较大源图时必须实际检查 Godot 缩放后的像素效果。

## 8.3 光线

推荐：

```text
画布：64×64
颜色：白色或灰度
背景：透明
线条通过中心
端点接触画布边缘
```

## 9. 每次修改后的验证清单

### 替换水晶图片

- 未点亮图片正确；
- 点亮图片正确；
- 状态切换正常；
- 图片居中；
- 没有拉伸变形。

### 替换镜面图片

- `/` 与 `\` 对应正确；
- 右键切换正常；
- 拖拽预览正常；
- 合法/非法反馈正常；
- 回收正常。

### 替换道具栏图标

- 正式图标显示；
- 占位符隐藏；
- 库存为零时灰显；
- 回收后恢复正常颜色；
- 图标没有被拉伸；
- 鼠标命中范围没有变化。

### 替换光线纹理

- `-` 正确；
- `|` 正确；
- `/` 正确；
- `\` 正确；
- 反射前后显示方向正确；
- 连续光段无明显断缝；
- 光路结束后全部消失；
- R 重置后无残留。

### 修改道具栏尺寸或位置

- 道具栏不超出屏幕；
- 不遮挡关键地图区域；
- 文字不被裁切；
- 图标比例正常；
- 拖拽命中正常；
- 库存数字正常；
- 目标分辨率下布局正常。

## 10. Git 协作流程

张梓涵修改美术或场景前，应从最新 `main` 创建个人分支，例如：

```powershell
git switch main
git pull
git switch -c art/zihan-replace-visual-assets
```

完成修改后检查：

```powershell
git status --short
git diff --check
git diff --stat
```

提交示例：

```powershell
git add -- <实际修改文件>
git commit -m "art: replace mirror and crystal visuals"
git push -u origin art/zihan-replace-visual-assets
```

通过 Pull Request 合并，不要直接覆盖其他人的功能分支。

### 不应提交

- 临时测试图；
- 未使用的重复资源；
- 编辑器缓存；
- 个人机器配置；
- 与本次任务无关的场景改动；
- 只为测试而修改但没有恢复的 `.tres` 字段。

## 12. 出现问题时的处理原则

### 图片没有显示

依次检查：

1. PNG 是否已被 Godot 导入；
2. `.tres` 是否保存；
3. 是否填入正确字段；
4. 图片是否有透明度但主体完全透明；
5. 是否在运行正确场景；
6. 是否误填入其他 Profile。

### 图片方向错误

检查：

- 镜面 `/` 与 `\` 是否填反；
- 光线 `slash` 与 `backslash` 是否填反；
- 不要忽略 Godot Y 轴向下。

### 修改大小后布局异常

检查：

- 是否修改了 Container 深层子节点；
- 父容器是否覆盖了手动 position；
- 文本是否撑大槽位；
- Theme separation 和 margin 是否变化；
- 目标分辨率是否不同。

### 视觉位置与碰撞或玩法位置不同

立即停止继续拖动。

这通常意味着只移动了视觉子节点，没有修改逻辑格。恢复改动并交由陈俊贤检查。

---

## 13. 最终原则

```text
换图片
→ 修改视觉Profile资源

调整UI大小与位置
→ 修改外层Control/Container布局

调整世界物件看起来的大小
→ 优先修改64×64图片内部构图

调整固定关卡物件的玩法位置
→ 不移动内部图片
→ 等待并使用后续Cell/LegalArea/WallLayer编辑接口

光线路径位置
→ 永远由传播逻辑生成
```

遵守以上边界，可以避免出现“画面看起来正确，但玩法实际位置错误”的问题。
