# 1. 总体原则

项目文件结构遵守以下原则：

1. `gameplay/` 保存可复用的游戏系统、公共协议、机关和运行模块；
2. `levels/` 保存关卡模板、单机关原型、组合原型、灰盒关卡和正式关卡；
3. `assets/` 保存美术、音频、视觉 Profile 和数据 Resource；
4. `tests/` 保存技术测试脚本和测试场景；
5. `docs/` 保存正式文档、API、操作指南和本地 AI 协作文档；
6. `user://` 保存运行时生成的日志、状态快照和存档，不进入 Git；
7. 核心运行控制器只负责引用、信号连接和生命周期协调；
8. 光线、光粒、库存、拖拽、目标、日志和自检必须分别放入独立模块；
9. 新增机关、光形态、目标或关卡时，原则上不得修改核心循环；
10. 现有代码采用行为保持式迁移，不推倒重写。

# 2. 项目根目录

```text
light-speed-singularity/
├─ assets/
├─ gameplay/
├─ levels/
├─ tests/
├─ docs/
├─ project.godot
├─ icon.svg
└─ README.md
```

| 路径 | 存储内容 | 主要作用 | 禁止放入 |
|---|---|---|---|
| `assets/` | 图片、音频、视觉 Profile、机关定义、关卡数据、成就数据 | 保存可被场景和脚本引用的资源 | 核心玩法脚本、正式关卡布局 |
| `gameplay/` | 核心协调、网格、传播、机关、库存、交互、诊断等 | 保存可复用玩法模块 | 正式关卡、章节专属布局 |
| `levels/` | 模板、原型、灰盒、正式关卡 | 保存具体关卡内容 | 通用机关脚本、核心系统 |
| `tests/` | 单元、集成、技术测试场景 | 验证模块和组合行为 | 正式选关内容 |
| `docs/` | 设计、规范、API、指南、AI上下文 | 统一项目知识 | 游戏运行时代码 |
| `project.godot` | 主场景、输入动作、项目设置 | Godot项目入口 | 关卡具体数据 |
| `README.md` | 安装、运行、构建、来源和项目介绍 | 面向仓库使用者 | 详细内部架构设计 |

# 5. `gameplay/core/`：核心协调层

目标文件（尚未实现；当前原型协调仍由 `core_loop_prototype.gd` 承担）：

```text
gameplay/core/
├─ level_runtime_controller.gd      # 目标 / 尚未实现

└─ run_state.gd                     # 目标 / 尚未实现
```

## 5.1 `level_runtime_controller.gd`

负责：

- 保存必要模块引用；
- 初始化和依赖校验；
- 连接信号；
- 接收开始运行请求；
- 接收发射请求；
- 调用光运行协调器；
- 接收统一执行完成结果；
- 协调目标判断；
- 协调全局重置。

不负责：

- 光线路径计算；
- 光粒 Tick；
- 镜面反射；
- 库存数量；
- 鼠标拖拽；
- UI细节；
- 日志文件写入；
- 具体水晶激活。

## 5.2 `run_state_controller.gd`

当前真实运行状态只有四个：

```text
SETUP
PULSE_ACTIVE
MOVE_WINDOW
COMPLETED
```

目标状态在 `SETUP` 与 `PULSE_ACTIVE` 之间增加 `READY_TO_FIRE`：

```text
SETUP

PULSE_ACTIVE
MOVE_WINDOW
COMPLETED
```

`READY_TO_FIRE` 与“开始运行按钮”均未实现，当前不在 `run_state_controller.gd` 中（该控制器本身亦为目标模块）。

同时负责：

- 状态切换；
- 发射权限；
- 布局编辑权限；
- 配置编辑权限；
- 状态变化信号。

## 5.3 `run_state.gd`

保存稳定的运行状态定义和公共状态数据，不保存具体玩法实现。

# 7. `gameplay/level/`：关卡世界层

目标文件（`level_object_registry.gd`、`level_validator.gd`、`level_world_query.gd` 均尚未实现）：

```text
gameplay/level/
├─ level_object_registry.gd      # 目标 / 尚未实现
├─ level_validator.gd            # 目标 / 尚未实现
├─ level_world_query.gd          # 目标 / 尚未实现
└─ level_config.gd               # 目标 / 尚未实现
```

## 7.1 `level_object_registry.gd`

负责扫描和注册：

- 固定发射器；
- 水晶；
- 预置机关；
- 受控对象；
- 关卡目标对象。

提供按 Cell、类型和 ID 查询。

## 7.2 `level_validator.gd`

负责只读检查：

- 发射器数量；
- 对象越界；
- 重复占用；
- 多格冲突；
- 缺失资源；
- 无效方向；
- 水晶组配置；
- 关卡库存配置。

只报告问题，不自动修改关卡。

## 7.3 `level_world_query.gd`

实现光传播所需的只读世界查询：

- 是否在地图内；
- 是否阻挡；
- 当前格的交互对象；
- 当前格的目标；
- 当前光形态是否可以通过；
- 固定对象与玩家放置对象的合并查询。

## 7.4 `level_config.gd`

保存当前关卡运行配置，例如：

- 地图边界；
- 运行期移动次数；
- 是否允许切换光形态；
- 关卡库存；
- 教学信息；
- 成就关联。

## 18.1 `runtime_logger.gd`

负责：

- 结构化日志；
- 内存缓冲；
- 文件轮转；
- 删除最旧文件；
- 日志等级；
- 模块标签。

RuntimeLogger 不向 Godot 控制台输出，只写入文件。日志文件位置为 `user://diagnostics/logs/runtime.log`。

默认限制：

- 单文件2 MiB；
- 最多8个日志；
- 日志目录16 MiB；
- 单快照1 MiB；
- 最多10个快照；
- 快照目录10 MiB。

## 18.2 `self_check_runner.gd` 与启动自检链

当前真实启动自检调度链：

```text
core_loop_prototype._ready()
→ 顺序执行七项启动检查
→ 每项调用 DiagnosticsController.run_self_check()
→ 每次临时创建 SelfCheckRunner
→ 每次注册并执行一项检查
→ 七项全部成功
→ 写一条 INFO 摘要到 user://diagnostics/logs/runtime.log
```

注意：

- “七次独立调用”只是当前实现事实，不是永久冻结架构；
- SelfCheckRunner 只汇总结果，不修改业务状态；
- RuntimeLogger 不输出 Godot 控制台。

## 18.3 `runtime_snapshot.gd`

已实现：

- `RuntimeSnapshotData`；
- 序列化（`RuntimeSnapshotJsonResult`）；
- 写入结果（`RuntimeSnapshotWriteResult`）；
- 文件保存能力。

未实现：

- 从真实玩法模块自动采样完整状态。

当前 RuntimeSnapshot 只支持“调用方提供 `RuntimeSnapshotData` → DiagnosticsController → 序列化或保存”，尚未接入真实玩法自动采样。真实采样的前置条件：

- 稳定的 `crystal_id`；
- `LevelObjectRegistry`；
- 多水晶统一注册；
- `ObjectiveController`；
- 正式 `LevelRuntimeController`。

禁止使用 `Node.name` 作为正式 `crystal_id`。

## 18.4 DiagnosticsController 边界

- `DiagnosticsController` `extends RefCounted`；
- 只长期持有 `RuntimeLogger`；
- 每次自检临时创建 `SelfCheckRunner`；
- 不长期持有玩法节点；
- 不修改玩法状态；
- 不决定玩法是否继续；
- 不承担玩法事务硬断言。

## 18.5 InventoryConsistency

纯数据快照和规则已经实现，六个运行期库存一致性硬断言边界已经接入玩法侧。Diagnostics 只负责启动/按需检查，不承担这些玩法事务断言。

- `levels/` 保存通用玩法脚本；
- `assets/` 保存关卡控制代码；
- 核心循环直接引用具体镜面、水晶、墙体纹理节点。

# 41. 最终验收标准

这套文件结构完成后，应满足：

- 核心循环只保留协调职责；
- 光线与光粒独立；
- 发射器只生成通用请求；
- 传播只通过世界查询读取关卡；
- 关卡制作不修改核心代码；
- 美术通过 Profile 替换；
- 固定对象可在 Godot 中拖动、复制和吸附；
- 技术测试和关卡原型分离；
- 日志不会无限增长；
- 新增机关不要求修改核心循环；
- 当前已完成代码被迁移复用，而不是重新实现；
- 每个文件都能明确回答“为什么放在这里”。
